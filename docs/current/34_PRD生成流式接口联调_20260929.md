# PRD 生成流式接口联调

> 最近更新：2026-09-29（Asia/Shanghai）。本页记录 `FROM_DEFINITION_CREATE_PRD` 的前端标签页、业务后端流式桥接和浏览器验证，不修改 `25_工作交接_项目功能PRD_UC_FR_CRUD_20260928.md`，也不修改 Agent 工程。

## 1. 目标

PRD 标签页顶部已增加“生成 PRD”，由前端以项目和功能身份发起真实流式请求。业务后端从只读项目数据库读取功能定义，调用 Agent 的 `FROM_DEFINITION_CREATE_PRD`，再把 Agent 的逐行 JSON 流转换成浏览器可消费的标准 SSE。

本阶段只完成流式生成链路，不创建正式 PRD、不保存草稿、不确认 PRD。

## 2. 浏览器接口

```text
POST /api/v1/agent/prd/generate/stream
Content-Type: application/json
Accept: text/event-stream
Cookie: ts_session=<HttpOnly session>
```

请求体：

```json
{
  "project_id": "项目 UUID",
  "function_id": "功能 UUID"
}
```

接口另支持可选 `version`；本轮 UI 不传，不把数据库 revision_no 当作文档版本。不传时，后端不会擅自把版本号写成固定值；Agent 应将未提供的版本标记为待确认。

浏览器不提交 `project`、`feature_name` 或 `function_definition`。这些内容必须由后端从当前用户有权访问的项目数据库读取，避免前端篡改上下文。

## 3. 项目名称不是 hardcode

后端使用数据库中当前项目的真实名称：

```text
数据库 project.name
        ↓
Agent inputs.project
        ↓
Agent message 中的“适用项目”
```

例如当前项目叫“测试项目1”，Agent 请求中就是“测试项目1”；如果换成其他项目，不需要改代码，也不会固定为“通用”。

## 4. 后端发送给 Agent 的请求

后端内部调用：

```text
POST http://192.168.64.3:8300/api/v1/agent/invoke/stream
X-API-Key: <只存在后端环境>
Content-Type: application/json
Accept: text/event-stream, application/json
```

请求体结构：

```json
{
  "message": "请根据以下功能定义生成完整的产品需求文档（PRD）……",
  "scene": "FROM_DEFINITION_CREATE_PRD",
  "inputs": {
    "feature_name": "数据库读取的功能名称",
    "project": "数据库读取的项目名称",
    "version": null
  },
  "reference_data": {
    "source": {
      "kind": "FUNCTION_DEFINITION",
      "project_id": "项目 UUID",
      "function_id": "功能 UUID"
    },
    "project": {
      "id": "项目 UUID",
      "name": "项目名称",
      "description": "项目简介"
    },
    "function": {
      "id": "功能 UUID",
      "name": "功能名称",
      "description": "功能定义正文"
    },
    "function_definition": "功能定义正文",
    "version": null
  },
  "response_format": "text",
  "trace_id": "业务后端请求 ID",
  "timeout_seconds": 300
}
```

`response_format` 是文本，不定义 output schema。Agent 返回的 `output` 应当是完整 PRD Markdown 正文。

## 5. 浏览器收到的业务 SSE

成功事件：

```text
data: {"type":"token","content":"# 需求背景"}

data: {"type":"token","content":"\\n\\n"}

data: {"type":"done","scene":"FROM_DEFINITION_CREATE_PRD","output":"完整 PRD Markdown","request_id":"...","trace_id":"..."}
```

失败事件：

```text
data: {"type":"error","code":"agent_timeout","message":"Agent 生成 PRD 超时，原输入已保留，请稍后重试。","request_id":"..."}
```

后端不会把 Agent 的 API Key、原始错误正文、`task_id` 或 `thread_id` 转发到浏览器。

## 8. 前端接入与代理防缓冲修复（2026-09-29）

- 前端新增 `src/features/prd/api.ts`：带 Cookie 的同源 POST、UTF-8 增量解码、SSE 分帧、只认有效 done、HTTP/SSE 错误与大小/时间限制、取消清理；不直连 Agent、不携带 API Key。
- `generation.ts` 与工作台 store 将生成预览独立存放；PRD 标签页增加生成/停止及原文/预览切换。生成中禁止原文写动作；完成不自动写库。停止/失败恢复“生成 PRD”，迟到结果无效。
- 完成后“已生成 PRD”禁用只是本轮内存预览的防重复默认。没有接入生成结果保存/确认；不改变已有手动 PRD 保存/确认流程。
- **浏览器发现并修复的真实问题**：Next 默认 gzip 压缩把 SSE 小片段缓冲，业务后端已发 token，但浏览器没有实时正文。只在业务 PRD 生成 SSE 响应加入 `Cache-Control: no-store, no-transform`，保留 `X-Accel-Buffering: no`；未关闭全站压缩、未改 Agent。
- Next `proxyTimeout` 从130秒提升到310秒，前端总超时315秒，覆盖后端300秒。公司额外反向代理若存在，仍需部署方验证不缓冲、空闲/总超时足够；本次不代表公司部署通过。
- 防缓冲复核（独立慢流注入，不是真实 Agent 速度）：通过 Next 的响应不再有 `Content-Encoding: gzip`，首事件0.015秒可读。证据 `proxy-and-smoke.json`；修复前证据 `buffering-before-fix.json`。
