## 1. 已确认的归属关系

| 层级 / 关系 | 统一口径 |
|---|---|
| 项目 → 业务功能 | 一对多；项目是团队与数据隔离边界 |
| 业务功能 → PRD | 一个稳定 PRD 对象，不是一个项目只有一个 PRD |
| 对象 → 版本 | 对象身份与正文版本分开；不把标签名字当版本 ID |
| PRD → UC → FR | 位于明确业务功能中，保留生成来源 |
| FR ↔ UC | 允许多来源；D02已确认正常新建/修正来源限同项目同业务功能UC当前已接受版本；有待审更新仍可选旧的当前接受版，既有引用不自动升级 |
| FR → 分配 | 分配与 FR 正文分开；一个 FR 可对应多个子系统目标 |
| 全景 | 基于对象与关联的派生视图，不另存可任意编辑的正文副本 |
| 子系统划分 | 不同项目可以不同，不强制全平台共用固定名单 |

数据库 V1.1 明确纠正旧的 `project_id` 单列 PRD 唯一约束。未来迁移不能恢复“一项目一 PRD”的旧模型。

## 2. 数据分层：设计建议，尚未实施

当前按V2.0分层；具体32张表、字段和组合键以11号文档为准，迁移仍未执行：

- **项目与业务功能**：归属、访问范围与生成边界。
- **对象身份及版本**：稳定对象 ID、正文/结构化数据、当前版本、接受状态与历史。
- **来源与关联**：生成所依据的上游对象和精确版本，而非只存可变名称。
- **任务与输入快照**：谁在何时、以哪一版输入发起何种生成；结果候选如何关联业务对象。
- **会话、消息、附件引用**：2026-09-21 用户改为项目级独立对话，同项目跨对象共享会话；不得因切换标签而改变会话。请求仍显式绑定目标功能/对象及输入快照，跨项目不共享。旧 V1.1 对象会话设计需在后端实施前修订，不代表已有数据库变更。
- **权限与审计**：页面能力、数据范围、对象动作独立于正文内容管理。

PRD正文整段保存于prd_versions.markdown_body（text），允许普通长文本，不要求章节结构化；UC 保存 12 个顶层字段及嵌套场景结构；FR 保留编号、来源和描述。UI 阅读卡片或 Figma 图层不直接决定数据库实体。

## 4. 业务后端与 Agent 的职责边界

| 层 | 应承担的职责 | 不能越界宣称 |
|---|---|---|
| 前端 | 展示、收集输入、编辑/接受等动作、明确等待与失败状态 | 浏览器持有服务端 Agent 密钥；本地保存等于服务端落库 |
| 业务后端 | 身份与权限、项目/功能/对象归属、输入快照、版本冲突、正式保存、接受状态、审计、业务任务关联 | 收到 Agent 成功后不校验就覆盖已接受版本 |
| Agent | 根据约定场景或编排产生内容/建议，返回结果及任务状态 | 自行决定正式对象权限、归属、接受与版本覆盖 |

以上为职责基线，不是已完成接口列表。数据库旧稿中的建议 API 路径不得作为现有业务后端接口使用；正式集成应以部署版本的后端 OpenAPI 与验收结果为准。

## 5. 任务与版本边界

**2026-09-21最新确认：**四类内容对象的新内容默认待审阅，修改形成新版本，旧已接受版本保留，只有显式接受才切换当前已接受版本；人工来源不自动接受。总体模型已批准，D02已确认正常FR来源选择资格，D07另行确认接受时的直接上游版本检查；撤销流程、并发实现和具体交互继续核对。见[14号确认记录](<E:/Git projects/TS-frontend/docs/current/14_Metadata自描述与规则驱动需求确认.md>)；当前代码与冻结SQL尚未实现该完整流程。

- D07：接受UC/FR/FR分配时，分别检查其引用PRD/每个来源UC/所引用FR仍为对应对象的当前已接受版本；根PRD无上游门槛。接受检查与提交须保持一致，不只信前端加载结果。
- 工作版更新但未接受，不使上游当前接受版失效；当前接受版已切换则阻止尚待接受的过时下游引用，人工复核并形成新修订后再接受，不静默改引用。
- 下游已经接受后，上游后续更新不改其正文、历史引用或接受结论；单独显示依据更新提示，不递归阻断全部间接依赖、不新增方案最新门槛。受控导入仍保持真实关系及待审阅状态，正式接受遵循同一规则。
- AI 完成、结果候选可读、业务正文保存、用户接受，是不同事件。
- 生成/修改业务对象的任务必须绑定明确业务功能、对象/创建意图及输入版本；结果不应覆盖期间变化的正文或引用。项目普通问答可无功能/对象目标，不能为满足旧表非空约束而伪造目标。
- 对旧结果、撤权、切换方案等情况的冲突校验属于后端待实施内容。
- V2.0的ai_runs保留waiting_human与ready；M1实施时需验证续接/取消协议，不把等待人工当失败/完成。
- 业务 `run_id`、Agent `task_id` 和会话 `thread_id` 需要建立关联，不应混用为同一个 ID。
- 当前 Agent 任务表为进程内存；SQLite 图检查点不等于业务任务持久化，不能用其替代上述设计。

以下仍属设计默认/待确认：项目、业务功能、单对象的授权粒度；生成、接受、归档、导出的独立动作；上级禁止访问时子对象授权是否穿透；项目架构负责人的发布权限。不能因为某个角色叫 editor 就假定其能发布全项目方案。
