## 3. 账号决策（不能再重新设计成每功能一个账号）

### 3.1 数据库层

|角色|类型|一期用途与权限|
|---|---|---|
|`ee_m0_owner`|既有NOLOGIN|对象所有者；API不用它。DDL/授权经DBA审核|
|`ee_project_api_ro`|既有LOGIN|25张表SELECT-only；不扩权为写账号|
|`ee_project_api_rw`|旧create原位改名的LOGIN|所有项目/功能共用业务写连接，24表SELECT、16表INSERT、仅artifacts.head_revision_id列UPDATE、2函数EXECUTE|

迁移是`ee_project_api_create → ee_project_api_rw`，不创建并存账号、不合并新旧账号。两个业务登录的SELECT允许有受控交集：普通读取使用ro，写事务中的读取校验使用rw同一连接，保证事务一致性。rw不是“只有写权限”，也不是全表全列CRUD管理员。以后新增能力复用rw，按版本追加必要授权；不预先授予DELETE/全表UPDATE/DDL。

允许rw SELECT的24表：projects、app_users、project_members、access_bindings、access_roles、role_permissions、permission_definitions、project_subsystem_designs、business_functions、artifact_types、artifact_type_versions、artifacts、artifact_revisions、prds、prd_versions、use_cases、uc_versions、uc_scenario_items、functional_requirements、fr_versions、fr_uc_sources、fr_allocations、allocation_versions、review_events。

允许rw INSERT的16表：projects、project_members、access_bindings、project_subsystem_designs、security_audit_events、business_functions、artifacts、artifact_revisions、prds、prd_versions、use_cases、uc_versions、uc_scenario_items、functional_requirements、fr_versions、fr_uc_sources。

函数只有`controlled_import()`判定和`accept_manual_revision(uuid,uuid,uuid,uuid,text)`受控接受。接受函数由ee_m0_owner持有，SECURITY DEFINER，固定`pg_catalog, ee, pg_temp`搜索路径并撤销PUBLIC EXECUTE。API没有直接更新accepted指针的权限。

**诚实的信任边界**：项目创建仍需要成员表/access_bindings的INSERT，持有DB写凭据的人理论上能绕过API插入应用授权。当前一期依赖后端密钥隔离及API项目/成员/动作检查，不代表数据库已经实现每个最终用户的独立行级隔离。不要把DB账号给最终用户。长期若要强化可另行收敛到窄函数，不在本次改名中大规模重构。既有PUBLIC TEMP策略未修改，“无DDL”指不能修改持久化业务schema结构。
