## 1. 已确认的核心要求

1. 覆盖现有PRD、UC、FR、FR分配，完整说明对象是什么、有哪些字段、怎么展示、哪些可编辑；不能用几列JSON或不完整字段目录替代交付。
2. metadata不仅用于说明或保存：后续前端与后端必须实际消费共同定义，不能各自硬编码另一套不一致规则。
3. 对已经支持的字段/控件，字段中文名称和展示顺序应由对应版本定义驱动；改变定义并在相应对象/视图使用该版本后，界面按定义显示。不是无版本、无审核地热改所有历史对象。
4. 字段只读规则同时约束前端编辑入口与后端提交；非法修改应被后端拒绝。字段可编辑性不能取代运行时用户权限、对象状态和版本冲突检查。
5. FR分配候选来源统一为本项目子系统目录，不能前端写一份固定候选、后端采用另一份规则。
6. 保留专用展示组件，包括UC嵌套合并表格，不把现有页面改成通用表单。新增完全不同的控件或业务行为仍可能需要开发。
7. 继续数据库先行、后续联调；本次先完成定义、存储和验证准备，后续实际接入前后端必须列入验收，不能在只存了定义时宣称整体完成。

## 2. 继承的对象规则

依据02号前端交互规范、03号职责边界及本轮用户确认，不重开已确认事项：

| 对象 | 内容与显示 | 已确认边界 |
|---|---|---|
| PRD | 整份自由Markdown/长文本；正文不强制章节结构 | 编辑整份正文，保存不等于接受 |
| UC | 12个顶层显示字段；场景内主流1行、分支4槽、异常5槽，保留合并分组 | 编号只读；整表编辑；展示空槽不等于伪造缺失源记录 |
| FR | 需求编号、需求来源、需求描述；来源关联真实UC及版本 | D01已确认待处理FR详情可用UC选择器增删/修正来源，保存新FR版本，旧关系不变；正常来源候选资格按已确认D02执行 |

项目/功能归属、编号身份、版本关系、来源外键、权限仍有受控字段/关联真源，不能全部降级为自由metadata。按已确认D03修改产生待审阅新版本、不覆盖已接受历史；空值/N/A/缺项不混同，不自动接受。

## 3. 定义的核对清单（细节仍待逐项冻结）

- 对象：稳定类型编码、中文名称、业务用途。
- 字段：稳定键、中文名称/解释、值类型、内容路径、嵌套/列表/引用结构。
- 显示：顺序、分组、视图、表格列/合并区、已支持的控件。
- 编辑：固定只读/可编辑/派生只读，所在视图的限制；运行时有效权限另由后端判定。
- 校验：必填/空值、枚举、多值、引用候选范围；草稿保存与接受要求分别确认。
- 版本：内容引用的规则版本、历史解释、规则升级适用范围。

以上不是已经确认每个字段的必填或接受条件，也不预定实际JSON字段名、OpenAPI路径或实施表数。最终契约须与后端OpenAPI、现有组件和数据库约束对齐。

### D03：统一对象/版本/接受模型（总体模型已确认，2026-09-21；细则待定）

用户针对“所有来源的新内容默认待审阅；修改产生新版本；旧已接受版本保留；只有显式接受才切换当前已接受版本”的总体模型回复“认可”。以下核心原则成为正式需求；这不是本轮立即执行SQL或接通AI更新的授权，也不等于把所有状态转换细节一并确认。

#### 已确认的共同原则

1. PRD/UC/FR/FR分配使用共同的版本与接受语义：人工、AI、导入是内容来源，不能据此自动授予接受状态；新保存内容默认待审阅。
2. 修改形成待审阅的新内容版本，不原地改写已接受历史。接受针对明确的内容版本，而不是永久作用于整个对象。
3. 当前工作版本与当前已接受版本可以不同；产生新候选不撤销旧版本接受，不把新正文配上旧版接受标签。
4. 有权限用户显式接受并校验通过后，才切换当前已接受版本。保存与接受是不同动作；AI完成也不等于接受。
5. 既有稳定对象身份、编号和版本来源追溯继续保留；该模型支持后续AI/人工基于已接受内容进行修订，但实际功能尚未实现。

#### 实施建议及仍需细化的部分

- 示例：r1已接受、r2工作版待审阅时，建议详情明确显示正在查看的版本，并标“有待审阅更新；当前已接受r1”，提供查看r1/差异入口；具体界面样式不由本轮确认替代。
- 建议一期一个主工作分支，暂不引入多人分支合并平台；分支/并发操作细节仍需技术审查。
- “已确认”和“已接受”建议统一文案；不在本轮直接修改UI文本。
- 新候选放弃/拒绝不应误伤旧版本接受；明确撤销、恢复、回退、可用性和审阅事件一致性须另行核对，不能只删除原有保护。
- 可选“保存并接受”若要提供，仍是两个明确业务动作并检查权限；本轮没有确认新增按钮、创建者自审权限或双人审批制度。

#### 各对象的版本/审阅单位建议

| 对象 | 内容改版/接受的单位 |
|---|---|
| PRD | 一份完整正文；文本不强拆章节，修改小段仍形成该PRD新版本 |
| UC | 单个UC的完整结构快照，包含场景；修改指定字段不改其他UC，不改变编号/身份 |
| FR | 一条FR的描述及明确UC来源关系；来源修改同样生成新FR版本 |
| FR分配 | 一个FR对应的一组子系统目标及采用的FR/方案版本；不修改FR正文，多选目标整体保持一致 |

FR分配继续保持既有选择交互，不引入整表编辑/保存模式；未来可即时保存待审阅工作版本，但保存与接受的入口/粒度需结合现有视图另行确定，当前不把“勾选”直接当作已接受。

#### 下游与AI安全边界建议

- FR固定引用UC的具体版本。UC新候选尚未接受时，不自动改FR来源，不撤销历史接受；可显示上游有待审更新。
- UC新版本接受后，仍引用旧版的FR保留原文/来源/审阅历史，单独标“上游依据已更新，待复核”；不是自动判FR错误，也不自动变更所有下游对象。对象级版本差异提示不等于已完成字段级影响分析。
- D02后续已确认：正常新选来源只用UC当前已接受版本；有新候选时仍可选旧的当前接受版并提示，不使用待审工作版。受控导入保留原始未接受来源事实，不伪造接受。
- 审阅、归档/活动、依赖变化提示、AI任务状态分开表达。AI运行/失败/取消不直接改变已有版本的接受结论。
- AI更新冻结目标对象、基版、输入引用和可改字段；返回后重新鉴权并检查目标/输入版本。变化或取消则冲突/失效，不覆盖人工保存；仅持短事务锁进行最终校验和提交，不在模型运行期间锁数据库。
- 接受只针对当前被审具体版本，不能把r1的接受事件应用到r2；拒绝r2也不能误撤销r1的接受。精确拒绝/撤销/恢复流程另作审查，不用“最后一条对象事件”直接推断所有版本状态。

#### 与metadata的关系

类型metadata描述字段/展示/允许动作/引用规则；实例响应由真实版本指针、版本审阅、权限和依赖关系计算可编辑/可接受/只读原因。权限和正式状态迁移仍由后端/数据库执行，不允许自由JSON脚本决定权限。内容创建来源与审阅结论分开，统一状态语义适用于四类对象，具体字段规则可不同。

#### 冻结包差距（代码事实，非新规则已实现）

- artifacts已有head_revision_id、accepted_revision_id、lock_version；artifact_revisions已有base_revision_id/type_version_id，review_events按revision_id记录事件。
- integrity.sql.inc中的guard_artifact_update目前禁止已有accepted_revision_id时变更head/accepted指针，因此原包并不支持上述已接受后再修订流程。
- check_artifact_complete当前以对象最后一条review事件核验接受指针；若批准“拒绝新候选而保留旧已接受版”，须重审版本级审阅和接受指针一致性，不能只删除前述保护。
- M0创建来源只允许manual/import/migration，AI任务三表及ai_run_id明确延期M1。本次讨论不代表已接入AI更新API，也不能通过metadata改值伪造AI任务。
- D03总体模型已获认可，后续须在细节明确后更新设计/触发器/版本级审阅测试、双版本展示及后端提交契约，并重新发布执行包；已接受历史不可变与权限校验必须保留。此轮不改旧包、不继续服务器步骤。

| FR分配 | 至少一个有效本项目子系统目标（已由D05确认），明确关联的FR版本与子系统方案版本 | 编号/来源/描述派生只读，只编辑目标 |

UC的参与者、前置条件、后置条件、扩展用例、HMI交互逻辑、法规需求、性能需求、非功能需求不作为一期系统强制非空项，可保留空值或真实填写的N/A；分支与异常仍固定显示槽位但不强制填满，原文缺项不自动造记录。非必填不表示不重要或无须人工检查，只是不以非空规则阻断接受。今后新增强制必填项须另行确认，不能由实现自行扩大本次清单。

校验只用非空白判定，不静默trim或重写所保存正文。编号、身份、类型、项目/功能、版本及系统审计值由系统保持完整且只读，不因为某业务正文非必填而允许破坏。保存阶段使用D05，不能在保存时错误套用接受阶段必填条件。

最低校验通过仍须有权限用户显式接受，不自动改变接受状态。N/A/TBD在关键必填项中的具体拒绝策略仍需审查；上游在审阅期间变版后的处理及分配接受时引用FR当前已接受版的门槛已由D07另行确认。本轮不改运行代码或类型种子。

### D07：接受时重新核对直接上游的当前已接受版本（已确认，2026-09-21）

用户对“接受时重新检查上游版本，但不自动改写或降级已接受下游”的规则回复“同意”。以下成为正式需求，尚未实现。D02规定正常新建/修正FR来源时能选什么；D07另外明确“选好之后、正式接受之前，上游可能已经变化”时的检查，并统一应用到下表的直接引用链。

**已确认原则：**接受下游候选版本时，其每一条直接上游引用都必须指向该上游对象在接受检查时的当前已接受版本；检查与接受提交须保持一致，不能只依赖页面加载时的结果。保存草稿不等于接受，本规则不把最低接受条件提前到草稿保存，也不授权随意选择不符合D02的来源。

| 被接受的对象 | 接受动作须检查的直接上游（已确认，待实现） | 范围说明 |
|---|---|---|
| PRD | 无 | 根对象仍按D06正文条件、权限及版本等规则接受，不新增上游门槛 |
| UC | 所引用的PRD版本 | 必须仍为对应PRD的当前已接受版本 |
| FR | 所引用的每一个UC版本 | 每条都必须仍为对应UC的当前已接受版本；至少一条仍按D05/D06 |
| FR分配 | 所引用的FR版本 | 必须仍为对应FR的当前已接受版本；子系统目标及方案版本继续按已有有效性规则检查 |

已确认的行为示例：

- UC r1已接受、r2待审阅：FR引用r1时，这项上游检查可通过；不要求等待r2，但不代表其他接受条件自动通过。
- FR仍待审阅、其引用的UC r2已取代r1成为当前已接受版本：阻止接受仍引用r1的FR，指出变化来源；人工复核后以新的FR修订版明确关联r2，再重新检查。不静默升级引用，不假定换引用即可保证正文正确。
- 引用的上游没有当前已接受版本：阻止接受下游。撤销/恢复上游接受的具体操作尚未确定，本条不授权新增该流程。
- FR此前已经接受，后来UC接受了新版本：不自动改写FR正文、历史引用或接受结论；单独显示“上游依据已更新，待复核”。该提示与接受状态分开，不强制自动生成新版本。

受控样本导入继续保留真实关系并全部待审阅；不为通过上游门槛伪造接受、偷换版本或给普通API开旁路。导入后的正式接受也须通过相同检查，可按PRD→UC→FR→FR分配的顺序逐级审阅。

本项仅检查直接上游，不递归阻断所有间接依赖；也不新增“子系统方案必须为最新版本”、自动修复、批量接受、自动降级或撤销规则。实际事务/并发控制及依赖提示的接口与展示须在后续实现设计中细化。
