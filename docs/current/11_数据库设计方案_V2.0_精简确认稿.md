## 2. 通用字段和完整性约定

1. 所有UUID由可信服务端生成；源编号code保留并按项目/功能/类型唯一，不用可变名称关联。UUID默认生成具体函数由迁移决定，字典“—”表示调用者提供，不表示自动NULL。
2. `text`正文允许保留原始换行、空白、N/A、无和TBD；空字符串不等于已确认不适用。名称/编号非空；UC描述/主流程等接受校验由类型schema约束。JSONB对象默认`{}`且限制对象形状；数组/schema根据用途另校验。
3. 字段表里的PK/FK/UQ“组成列”不表示该列单独唯一，**准确列序列见该表键清单**。所有FK目标组合都列出了相应PK/UQ，不用只校验单个UUID存在。
4. `updated_at`在写事务中显式更新；now()只作为插入默认，并不会自动处理UPDATE。bigint/integer的版本号>0、lock_version≥0、顺序≥0。
5. 删除策略默认RESTRICT/NO ACTION，历史和已引用身份不级联删除；归档和关闭Tab不是物理删除。不存在“任何表统一ON DELETE CASCADE”。
6. 内容历史不可覆盖；允许改的控制状态单独列清：artifacts指针/锁、方案current指针、角色成员、任务进度/输出状态、类型retired_at。JSON schema/版本正文/来源/目标及审阅事件仍不可修改。
7. 版本头→具体正文必须恰好一种正确类型且有对应身份；固定type_code＋组合FK防串类型，缺失子表/缺场景属于跨表完整性，需受控事务及提交检查/约束触发器。[PG-C]
8. 仅看FK无法保证“可分配”“有权限”“已接受”“当前方案”；写入事务还需做语义检查。scope CHECK必须约束可空字段的合法形状，不能依赖带NULL的组合FK替你完成。[PG-C]
9. M0不创建AI字段/FK；M1按依赖顺序补齐。迁移版本表由选定迁移框架管理，不另建第二张业务schema_version表。
10. 不做权限缓存的M0每次查成员/角色/能力；事务提交前仍需鉴权。禁止用数据库超级用户或浏览器直连代替业务权限。

## 4. 当前32张表的完整结构

### 4.1 `projects`

**用途：** 项目是团队、数据与权限隔离的最高业务边界。  
**阶段：** M0 CRUD

| 字段 | 数据类型 | 可空 | 默认/提供方式 | 键/校验 | 字段作用 |
|---|---|---|---|---|---|
| `id` | `uuid` | 否 | — | PK组成列 | 项目稳定标识 |
| `code` | `text` | 否 | — | UQ组成列（见下） | 项目业务编号，创建后稳定且不复用 |
| `name` | `text` | 否 | — | — | 项目名称 |
| `description` | `text` | 是 | — | — | 项目说明 |
| `metadata` | `jsonb` | 否 | {} | — | 非核心扩展信息 |
| `lock_version` | `bigint` | 否 | 0 | — | 项目属性并发控制令牌 |
| `created_by` | `uuid` | 否 | — | FK组成列（见下） | 创建人 |
| `created_at` | `timestamptz` | 否 | now() | — | 创建时间 |
| `updated_at` | `timestamptz` | 否 | now() | — | 最后修改时间 |
| `archived_at` | `timestamptz` | 是 | — | — | 归档时间 |

**主键与唯一键：**
- PK (id)
- UQ (code)

**外键（源列 → 目标表列）：**
- (created_by) → `app_users` (id)

**业务校验与写入规则：**
- UQ(code)

## 5. 跨表事务设计审查：删掉复杂设施后怎么保证正确

### 5.1 内容版本的原子写入

同一事务：重新鉴权 → 锁目标对象 → 比较expected_head_revision_id/lock_version → 分配revision_no → 写版本头和恰好一个正文子表 → 写场景/来源/目标 → 完整性校验 → 更新head/lock → 提交。版本号在锁内分配，不能裸MAX+1。首个PRD成功才建立可见功能目录；失败候选可在隔离任务区保存，不能占住正式目录。

版本FK和head/accepted指针形成环：迁移先建表及PK/UQ，再添加可空/延迟指针FK。普通内容引用使用明确组合FK；具体是否DEFERRABLE由迁移测试确认，不一律延迟全部约束。

### 5.2 删除epoch后仍必须检查完整输入集合

M1启动任务：在所属功能的短事务锁内，冻结完整primary输入及修订目标基版，记录 `(object_id,revision_id,role)` 和规范化集合摘要，然后释放事务调用模型。所有改变该功能的对象创建/归档/head/接受状态的写入也必须参与同一功能锁协议。

完成任务：重新鉴权，在同样短事务锁内重新列举有效输入集合，**比较实际集合及版本，而非只检查原有对象是否还在**；发现新增UC、归档UC、输入换版、目标被改均进入conflict，不覆盖用户编辑。分配另比较当前方案ID；所有方案改变也遵守项目/方案锁协议。角色/授权变更需与业务提交协调，采用固定锁顺序（角色定义→项目→功能→对象，批量对象ID排序），不在模型响应期间持锁。[PG-L]

不做分布式租约不等于没有迟到保护：取消/重试各有任务ID，完成时锁任务并CAS检查状态；失效任务不可更新head。输入查询失败、不可读或不完整不得静默改成“有权看到的子集”。

### 5.3 子系统历史而非发布审批

默认“保存有效新方案→切换current”，用方案入口lock_version控制并发。保存前可用前端草稿/后端临时候选承载尚未选用内容，但不把独立正式发布审批强行写入业务。一个项目多个并行方案仍待确认，当前数据结构只允许一个入口/当前版本。

分配修改固定FR版本与当前方案版本，只改变目标不复制FR描述。方案改名/拆并产生新版；历史显示从旧条目读；不复制一份subsystem_name_snapshot。旧分配保留并提示依据已变，不能自动认定语义错误，也不自动转移全部目标。

### 5.4 权限与审阅不因精简丢失

M0必须包含五张权限表，不允许先把业务API裸露出来再补权限。先启用项目级测试角色；功能/单对象继承规则未确认前，不启用相应绑定接口。任何进入、读、改、接受等动作仍按能力检查；不从“editor”名字推导权限。

accept事件与accepted指针在同一事务更新；保存只更新head。UC生成使用已接受PRD的规则保持。D07已确认接受时检查直接上游当前已接受版：UC查引用PRD、FR查每个来源UC、分配查所引用FR；无当前接受版或引用已过时则拒绝，不能只信请求携带的旧校验结果。检查与接受提交需在一致的事务顺序中完成；若下游先接受、之后上游才更新，保留已接受历史并单独提示。不递归阻断间接依赖，不要求接受时子系统方案必须最新，受控导入后的接受也遵守同一规则。具体锁/并发/错误响应机制仍待实现审查。恢复已生效旧内容是新版本；取消未接受草稿只是审阅/指针操作，历史仍保留。

### 5.5 导入与真实样本

通过09号核查的候选是1PRD/3UC/14FR/16条来源/14个分配对象与目标/7个名称。来源缺分支与系统名称差异未因本轮结构调整自动解决；默认pending。每批输入哈希、目标项目/功能、原始编号、sheet/table/row及转换规则记录在受控批次清单和版本metadata，不新增通用ETL平台。

相同批次重跑复用已存在映射/返回已完成，原编号冲突先比对，不静默覆盖。导入事务失败回滚整套关系；操作者/时间用当前真实导入人，不伪造历史接受/AI任务。PRD→UC关联注明“导入确认关联”，不声称证明了历史生成因果。

## 6. 迁移依赖与CRUD实施顺序

1. **M0表结构**：app_users → projects/business_functions/project_members → 能力/角色/绑定/审计 → artifact_types/artifact_type_versions → artifacts/artifact_revisions（不带ai_run_id） → 四类身份/正文、场景/来源、项目方案四表和分配关系 → review_events。
2. **补环与校验**：先存在表、主键、所有FK目标组合UQ，再添加head/accepted/current指针和其他FK；提交完整性与缺子表测试不可省。种子按用户→项目→功能→PRD→UC→FR，方案→分配依赖顺序写入。
3. **M0数据验收**：未登录/只读/跨项目拒绝、保存pending、接受原子性、类型FK、来源同项目同功能、方案混版拒绝、并发409、失败回滚、导入重跑不重复、读历史不漂移。
4. **M0接口联调**：业务后端提供OpenAPI，前端通过业务API而不是直连数据库；浏览器刷新/后端重启后仍能读取落库数据。已有PRD自动扩写真接口不等于其余CRUD已落地。
5. **M1增补**：建立ai_runs → 添加artifact_revisions.ai_run_id及FK/UQ → 建inputs/outputs → 初始化阶段白名单、waiting_human协议、候选状态/输入全集校验。不能只加三张空表就宣称AI持久化完成。

业务运行账号不得超级用户；迁移账号与运行账号隔离。服务器操作、账号口令和SQL仍由用户后续手动执行，本轮不执行。
