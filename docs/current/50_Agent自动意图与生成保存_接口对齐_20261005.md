# 本轮接口对齐与安全边界

状态：本地实现及契约Mock自动化验证通过；用户本地手工验收待进行。真实公司Agent需按以下契约单独验收，不能宣称已支持。

## 新生产生成入口
POST /v1/projects/{project_id}/functions/{function_id}/uc-generations/append
请求：client_request_id（UUIDv4）、prd_id、prd_revision_id。
POST /v1/projects/{project_id}/functions/{function_id}/fr-generations/append
请求：client_request_id（UUIDv4）。
均需原有会话Cookie、允许的Origin和X-Project-Request: 1，以及业务写开关和对象创建权限。
返回：generation_id、kind、status=succeeded、project_id、function_id、source_version、replayed、items（artifact_id、revision_id、function_id、created）。一批全部待确认；事务提交与回执一起保存于现有artifact metadata，不新增表或数据库迁移。replayed=true表示历史创建回执，不代表将已有对象重新改为待确认或恢复已删除对象。
旧只读UC/FR生成API不改变，联调预览继续writes=false。UC最多4个分支、5个异常；不足使用空槽位，超过则明确拒绝整批，绝不截断或擅自丢弃正文。

## 自动意图：现有聊天流端点
前端发送client_request_id、message、auto_intent=true、attachments；不再提交用户选择的mode。旧调用者仍可提交原question/modify模式，auto_intent缺省false保持兼容。数据库mode保留其旧含义（请求的基础模式），不是Agent推断结果；自动意图标记参与请求指纹，不需要修改数据库枚举。

后端分两阶段调用Agent，不使用本地关键词猜用户意图：
1. 先调用现有JSON invoke接口，response_format=json，要求唯一结构为 `{"intent":"question"}` 或 `{"intent":"modify"}`。意图阶段idempotency_key为原client_request_id加`:intent-v1`；同一重试稳定。
2. question走原text/SSE流；modify先检查当前附件的修改权限与版本，再走原JSON changes预览协议。两阶段沿用同一项目、后端thread_id和请求trace_id；执行阶段使用原client_request_id。
意图阶段的额外请求会增加一次模型调用；这是真实实现，不宣称单次调用或即时首字输出。SSE先发status提示，再发回答token或修改preview；禁止向浏览器展示内部意图JSON。

## 无附件与修改授权
当前attachments=[]，不补入当前标签、function_id、artifact_id、revision_id或正文。project_id、thread_id和历史messages正常保留；后端读取当前用户/项目/thread的有序历史问答，分别作为user/assistant消息发送，当前提问在message；新thread不带其他thread历史。历史附件不能提升为本次修改目标。无当前附件却被识别为modify时返回modification_attachment_required，不调用修改生成，不写业务对象。
修改候选精确绑定当前显式附件和base_revision_id，保留预览→采纳新待确认修订→人工确认的既有流程。Agent返回非法意图、非法对象、异项目ID或版本不符均失败关闭，不自动降级执行。

## UC图
自动打开仅在存在有效图代码时发送known_uc_source_version；显式刷新发送null，因此重新调用Agent。生产UI只对最新已确认UC出图。Mermaid依赖已锁定本地安装版本；禁用图内配置和外部交互，strict渲染后作为不可交互SVG图片展示，代码折叠可查。
