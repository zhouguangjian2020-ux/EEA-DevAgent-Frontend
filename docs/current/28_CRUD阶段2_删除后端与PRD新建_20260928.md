| 删除对象 | 已实现规则 |

### 2.1 输入、预检查和成功结果

- DELETE无请求体；query必填mutation_id（UUIDv4）及base_lock_version（0至bigint上限的规范十进制字符串）。拒绝额外/重复参数、cascade、force及任何请求体。
- 复用HttpOnly Cookie、Origin白名单、X-Project-Request: 1、Content-Type: application/json；actor从会话取得。
- GET返回target（真实ID/项目/功能/类型/编号/字符串版本/head/accepted）、can_delete、blocked、blocker_count及最多20个摘要。超限标blockers_truncated，但提交检查全部依赖。
- **can_delete表示授权及写开关，不代表无依赖**；前端后续须结合blocked。摘要标记head、accepted、stable_identity。
- 分配返回真实allocation ID、所属FR及当前head/accepted的子系统影响，空分配仍为真实对象。
- 成功200返回原mutation_id、目标ID、kind、archived_at、新字符串lock_version、history_preserved=true。
- 相同ID/原请求重试返回原结果，只写一次审计；跨目标/动作或不同版本复用ID返回409；新操作对已删对象返回404。
- 重放仍核验当前用户/成员/角色权限；仅匹配的删除审计允许在归档项目上重放，不开放新写入或普通读取。
- 错误含request_id、no-store：401未登录、403无权限/防护失败、404无访问或已删、409依赖/版本/操作冲突、422输入非法、503未配置/不可用、504超时；不暴露SQL或凭据。

### 2.2 并发与原子性

同项目业务API写入共用项目行锁，之后锁功能/对象。归档、版本与审计同事务，审计失败全部回滚，原操作可重试。

事件控制的确定性并发已覆盖两个提交次序：删除先拿锁则保存/确认失败；保存/确认先提交则旧版本删除409；新增UC来源先写则UC删除409，UC先删除则新增来源失败。不是依赖sleep碰运气。

此协议保护业务API及配套窄确认函数；不声称拥有DBA/服务账号凭据的人绕过API任意执行SQL也受完整业务规则约束。rw仍是后端专用账号。
