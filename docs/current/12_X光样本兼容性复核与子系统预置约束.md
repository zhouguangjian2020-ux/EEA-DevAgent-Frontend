## 3. PRD、UC、FR的具体映射与数据缺口

### 3.1 PRD按全文保存

- `markdown_body`虽然沿用这个字段名，实际类型为`text`，保存一整段普通文本或Markdown均可。
- 不新增“背景/目标/功能/性能”等必填章节列，不要求PRD先解析成JSON；类型schema也不能把章节齐全作为正文保存前提。
- 项目、功能、对象身份和版本元数据仍结构化，只有正文不强制结构化；一功能一个PRD对象规则不变。
- 保存正文不能用trim/拆段重组等操作静默改写原文；摘要、章节索引若以后需要，应派生而不替代全文。
- **现有转换稿不是无损Word导入器**：PRD正文有14处显式`w:numPr`，UC正文有52处。旧`inspect_case_data.py`读取文字和合并表格，但未解析`numbering.xml`，可能丢自动列表序号。后续正式转换必须保留/核对编号，尤其是“回到主事件流3”这类引用。若用户直接提供长文本，则无需Word转换。
- 原始Word排版、页眉图片、附件二进制并未由上述正文列承诺保存；当前32表没有通用附件持久化表。本轮是数据结构审查，没有进行Word逐页渲染或排版复刻。

## 6. Agent做FR分配的约束（待后端/Agent实施）

1. 后端从请求项目读取`current_version_id`，取该版本`is_allocatable=true`的条目；身份、名称、描述、域和已提供的职责范围一起作为输入，不能只发名称。
2. 固定FR输入版本集合和方案版本。M1已有`ai_runs.subsystem_design_version_id`用于关联这次读取的不可变目录版本；不再保存一份重复catalog_snapshot。
3. 结果返回FR身份及目录内`subsystem_id`集合（或受控稳定code后由后端解析），附分配理由。不能把自由文本名称直接当数据库外键。
4. 后端校验项目、方案版本、FR版本、条目存在且可分配。未知ID、跨项目、混版本、重复目标等按契约拒绝或去重，不创建目录项，不静默接受。
5. 当前方案或FR输入在运行中变更时，不能把旧候选伪装成新方案分配；进入冲突/重算流程。未预置、无可选项或没有合适目标时，返回待处理信息，不能发明新系统。空目标是否可正式接受仍待确认。
6. 成功后写独立`fr_allocations / allocation_versions / allocation_targets`，分配版本固定`design_version_id`；目标已有组合FK指向同项目同版本条目。人工选择与Agent选择共用同一目录及校验。
7. 目录换版不重写旧分配历史。不要把Agent建议完成等同于用户接受。

这些是新增明确的实施约束，不是已部署接口或本轮新开发的能力。
