## 2. P-001：项目权限设置

### 2.1 用户已提出并登记的需求

在顶部工具栏右上角增加“项目权限设置”入口。该功能暂不实施，先进入待实现列表。

用户确认的默认规则：

1. 创建项目时，创建人自动获得该项目的`project_api_author`。
2. 同一项目的其他成员默认获得该项目的`project_api_reader`。
3. 项目权限设置中可以添加协作成员。
4. 可以搜索用户，并按部门筛选用户。
5. 支持多选用户后统一授权。
6. 可以给用户配置项目内具体功能的权限，而不是只能给整个项目一个粗粒度角色。
7. 可以移除已经授予的权限。
8. 例子：用户A可以协作完成某个功能下的UC，但对同一功能的PRD只有只读权限。

### 2.2 预期入口和基本交互（待确认细节）

建议的交互流程如下，作为后续讨论底稿，不是最终UI定稿：

1. 在顶部工具栏右上角点击“项目权限设置”。
2. 打开当前项目的权限设置面板或页面。
3. 面板按“项目成员”和“功能权限”组织：
   - 项目成员：查看、搜索、按部门筛选、添加、移除或降级成员。
   - 功能权限：选择一个或多个功能，再选择用户和权限，批量授予或撤销。
4. 已有权限的用户显示当前权限来源和范围，避免用户看不出权限是项目默认权限还是某个功能的额外授权。
5. 保存后显示变更摘要，并记录操作人、被授权人、项目、功能、权限、时间和变更原因（原因是否必填待确认）。

### 2.3 权限表达方式（已确认部分与待确认部分）

为了支持“UC可协作、PRD只读”这种场景，建议将权限拆为：

- **项目级权限**：进入项目、查看项目成员、查看项目内容、管理项目权限等。
- **功能级权限**：针对某一个功能，对PRD、UC、FR分别授予读取、创建、编辑、确认等能力。
- **对象级权限**：本需求暂不默认展开到单个PRD/UC/FR对象；如果以后需要单对象共享，再单独增加需求。

已确认的UC协作权限与仍待确认的其他对象权限：

| 资源 | 建议动作 |
|---|---|
| 项目 | 查看、管理项目成员/权限 |
| 功能 | 查看、编辑功能基本信息 |
| PRD | 只读、编辑、确认 |
| UC | 协作权限包：读取、创建、编辑草稿、保存新修订、确认、生成、导出；不单独拆出“确认”权限 |
| FR | 只读、创建、编辑、确认 |

“用户A能协作UC但只能读PRD”按已确认的权限继承方式表达为：

```text
项目A + 功能F + 用户A
UC：协作权限包（读取/创建/编辑草稿/保存新修订/确认/生成/导出）
PRD：读取
FR：未授权或按项目默认权限处理
```

已确认：UC“协作完成”包含读取、创建、编辑草稿、保存新修订、确认、生成、导出；产品权限设置界面不把“确认UC”单独拆成一个授权项。PRD和FR的动作组合仍需后续确认。

### 2.4 2026-09-24 已确认的权限规则

以下规则已由用户确认，后续方案和实现必须遵循：

1. **项目权限管理者只有项目创建人。**普通`project_api_author`不能自动管理项目权限，`project_api_reader`不能管理项目权限。项目创建人移除、转移所有权等边界后续另行设计。
2. **新成员默认获得项目级reader。**加入项目后可以查看项目内容；额外写权限通过功能级授权单独授予。
3. **UC协作权限不拆分确认动作。**UC协作权限包包含读取、创建、编辑草稿、保存新修订、确认、生成、导出；界面上不单独配置“确认UC”。
4. **移除权限分为两种操作。**撤销某个功能权限不等于移除项目成员；移除项目成员会使其失去项目访问权。
5. **用户选择范围暂定为用户名搜索 + 部门筛选。**本期不扩展为显示名称、邮箱等其他搜索条件，除非后续重新确认。
6. **权限继承采用“项目reader + 功能级额外权限”。**用户可以保持项目级reader，同时只在指定功能上获得UC协作等额外权限，不因此获得其他功能或其他对象的写权限。

## 3. 当前实现事实核对

### 3.1 新项目默认授权

当前后端创建项目逻辑已经按以下方向设计：

- 业务写入开关和写账号配置就绪时，新项目创建人自动绑定`project_api_author`。
- 新项目创建人的项目成员关系、项目读取绑定、空子系统入口和审计记录在同一事务中创建。
- 其他成员不会因为创建项目自动获得成员资格；加入项目后默认应为`project_api_reader`，这一条需要在成员管理接口实施时固化。
- 如果在`BUSINESS_WRITES_ENABLED=false`时创建项目，当前实现会先按只读角色初始化；正式部署时应在写能力就绪后再开放该流程。

因此，**未来每新建一个项目不需要人工执行一次数据库授权**。当前需要单独绑定的是本次迁移前已经存在的历史项目，不是日常新项目流程。

### 3.2 当前权限仍是项目级

当前一期`project_api_author`包含项目读取、功能创建以及PRD/UC/FR的创建、更新、确认能力；当前后端授权查询按项目范围判断。

虽然`ee.access_bindings`表结构中已经预留了`function_id`和`artifact_id`字段，但当前R2约束仍要求：

```text
scope_kind = 'project'
```

当前没有经过实施和验收的功能级授权接口，也不能直接把预留字段当成已经支持的功能。要实现P-001，必须重新设计并审核：

- 功能级绑定的唯一性和覆盖规则；
- 项目级默认权限与功能级例外权限的优先级；
- 读权限是否可以继承，写权限是否必须显式授予；
- 用户被移除项目后，功能级授权是否自动失效；
- 一个用户是否可以同时拥有多个功能级角色。

### 3.3 当前部门字段情况

当前数据库`ee.app_users`表字段为：

```text
id
external_subject
display_name
email
state
metadata
created_at
updated_at
```

**当前没有独立的`department`、`department_id`或`department_code`字段。**

后端演示接口返回的`department`字段目前来自演示用户对象的硬编码值，不能代表公司用户主数据，也不能用于真实的部门搜索和筛选。

`metadata`虽然是JSONB字段，但当前没有形成部门字段约定、索引、数据来源或同步规则；本需求不建议直接把任意JSON内容当成正式部门数据。

## 5. 必须先确认的问题

### Q1. 谁可以打开和保存“项目权限设置”？——已确认

只有项目创建人可以管理项目权限。普通`project_api_author`不能自动管理权限，`project_api_reader`不能管理权限。创建人移除、转移所有权、创建人账号失效后的接管规则尚未设计。

### Q2. “添加成员”后的默认范围——已确认

新成员加入项目后默认获得项目级`project_api_reader`，可以查看项目内容；写权限再按功能单独授予。

### Q3. 功能级权限的动作范围——UC部分已确认

UC协作权限包包含：

- 查看；
- 创建；
- 编辑草稿；
- 保存新修订；
- 确认；
- 生成；
- 导出。

“确认UC”不单独作为一个可选授权项，而是包含在UC协作权限包中。PRD和FR是否使用相同动作组合，仍需后续确认。

### Q4. 移除权限的含义——已确认

界面必须区分两种操作：

1. **撤销某个功能权限**：用户仍是项目成员，但不再拥有该功能的额外权限。
2. **移除项目成员**：用户失去该项目的访问权。

不能把“撤销UC协作权限”误做成“移出项目”。

### Q5. 用户搜索范围——已确认本期范围

本期只支持：

- 按用户名搜索；
- 按部门筛选。

本期不扩展显示名称、邮箱等其他搜索字段。可搜索用户的组织范围和禁用用户排除规则仍需在数据源设计时确认。

### Q6. 部门字段的来源和形态

当前没有正式部门字段。需要确认：

- 部门来自现有公司认证/组织系统，还是由本系统维护？
- 一个用户是否只有一个当前部门，还是可能属于多个部门？
- 是否需要部门层级（事业部/部门/小组）？
- 部门变更是否需要保留历史？

建议第一版只支持“一个当前部门 + 稳定部门编码 + 显示名称”，由公司用户主数据同步；如果没有可靠的公司主数据接口，再讨论本系统维护部门表。

### Q7. 旧项目的一次性迁移策略

本次数据库改名已经完成，但历史项目不会被自动批量升级。需要明确本次要给哪个已有项目、哪个成员绑定author；这不影响未来新建项目自动给创建人author。

本期已确认的权限模型是“项目reader + 指定功能的额外权限”：用户不需要被提升为整个项目的author，也可以只在指定功能上获得UC协作权限。

### 9.3 八个场景及用户已明确的触发方式

#### P-002-01：提示词扩写 — `PROMPT_EXPAND`

- **触发**：在工作台对话框点击“一键扩写”。
- **后端**：接收当前输入文本，经统一业务接口调用Agent的`PROMPT_EXPAND`。
- **结果**：将返回文本回填到原项目的输入框，不自动发送、不进入功能创建或PRD生成链路。
- 失败或停止时保留原输入；跨项目结果不得回填到其他项目。输入在等待期间被用户修改时如何处理、按钮适用模式、是否原生流式，仍需最终接口/交互设计。

#### P-002-02：生成功能名称与描述 — `FEATURE_DEFINITION`

- **触发**：工作台选择“生成PRD”快捷按钮，输入内容后点击发送。
- **第一次Agent调用**：使用非流式`FEATURE_DEFINITION`；2026-10-06用户澄清功能名来自返回plan。当前适配按`plan.feature_name`取名，描述按该场景文本output处理（真实非流式字段样本待核对），不从流式文本猜名字，不强制改成json输出。分步需求和实施状态见52号。
- **功能识别（已确认）**：只在当前项目查找类似功能，展示候选名称和描述供用户确认；多个候选由用户选择，不自动合并。相似性算法和阈值仍待正式设计。
- **有候选时**：提示“该功能已存在，是否确认是该功能？”，由用户选择“是”或“不是”；不得由Agent或后端擅自替用户选择。
  - 选择“是”：定位用户确认的已有功能；若已有PRD则报错，不再调用PRD生成；若没有PRD则继续P-002-03。
  - 选择“不是”：创建新的功能，更新前端各工作空间中的同一功能身份；新功能默认被确认，自动继续P-002-03。
- **无相似候选时（已确认）**：直接创建新功能并继续PRD生成，不额外弹确认。
- “功能默认被确认”是用户确认的产品语义，**不表示PRD/UC/FR自动确认**，也不据此臆造已有数据库状态字段。
- 后端生成了名称和描述后不能重复要求用户手动再填一次；用户选择“不是”但名称完全相同时，**提示调整名称后再创建**，不按名称合并功能身份（已确认）。已有功能基本信息不得被本次候选结果静默覆盖。

#### P-002-03：生成PRD — `FROM_DEFINITION_CREATE_PRD`

- **触发**：同一次工作台“生成PRD→发送”流程，在P-002-02完成创建或定位且未报错后，由后端自动执行第二次Agent调用；不是要求用户再点一次发送。
- **来源**：已经创建或定位的功能定义。建议使用后端读取的功能名称/描述，并保留原始用户提示词中未包含在短描述里的要求；具体上游payload仍待确认。
- **前置规则（已确认）**：只要存在PRD对象，即使为空白、待处理或已确认，都必须阻止再次生成，提供打开已有PRD的入口；不覆盖、不新建第二份PRD。
- **成功（已确认）**：生成PRD后保存为待处理版本，自动打开既有PRD预览/编辑标签；不自动确认。
- **失败（已确认）**：保留已经创建且默认确认的新功能，并在各工作空间可见；提供重试PRD，重试复用同一个功能，不再创建功能。
- 功能确认与PRD审核属于不同阶段；不得把“功能默认确认”解释成“PRD默认确认”。

#### P-002-04：生成UC — `FROM_PRD_CREATE_UC`

- **触发**：点击现有PRD内容下方的生成UC快捷按钮，将当前Mock生成替换为真实Agent调用。
- **来源与门槛（已确认）**：当前功能的PRD已确认后才允许生成UC；业务后端读取并校验其身份、内容和精确确认版本。
- **结果（已确认）**：一次生成多个UC，数量按内容决定，不沿用Mock固定的3个。数量上限和结构校验参数在正式设计中确定。
- 现有UC的12个顶层字段、场景中的分支/异常结构必须保留并映射，不将自由文本直接当成可落库UC。
- 本条只确认PRD下方的批量入口；不把工作台其他“补充单个UC”入口擅自并入本次。

#### P-002-05：生成UC图 — `FROM_UC_CREATE_UC_DIAGRAM`

- **触发**：每次打开或重新展示UC全景标签页，自动展示该范围内所有已经被确认的UC的UC diagram。
- **来源范围**：当前项目、当前业务功能下全部已确认UC，不混入其他功能的UC或未确认草稿；遵循既有确认版本基线，r1已确认而r2待处理时不得把r2当成已确认内容。
- **已确认目标**：全景自动展示已确认UC的图。“来源不变复用、来源变化重生成”按用户“先保留”保留为候选，尚未定稿；缓存、失效和调用频率见9.5及Q10。
- 当前基线中UC图是只读派生视图；不增加节点编辑、拖拽写回源UC等未经提出的能力。
- **图的语义（已确认）**：一张包含参与者及全部已确认用例关系的综合用例图，不是每个UC各一张执行流程图。
- **生成与展示（已确认）**：后端向Agent发送该scene的生成指令，Agent返回图形代码，再由前端绘图组件渲染展示。Mermaid或其他绘图组件尚未选定，图形代码格式和schema仍待设计；不能把讨论中提及Mermaid写成已确定依赖。

#### P-002-06：生成FR — `FROM_UC_CREATE_FR`

- **触发**：在UC全景视图设置“一键生成FR”快捷按钮，点击生成当前范围的全部FR。
- 优先改造/复用已有Mock按钮，不重复增加同义入口。
- **来源**：当前范围内的UC集合；FR需保留精确UC来源关系，不能只用名称猜测关联。
- **生成门槛（已确认）**：当前功能全部有效UC已确认后才允许生成FR，不改成只处理其中的已确认子集；仍保留现有非空来源等检查。
- 返回FR集合，数量按内容决定，不继承“每UC恰好2条”的Mock数量（已确认）；去重、重复生成、数量上限和具体保存策略仍待设计/确认。

#### P-002-07：生成FR分配 — `FROM_FR_CREATE_SS_ASSIGNMENT`

- **触发**：在FR全景视图设置快捷按钮，点击一键生成所有FR分配。
- **来源与门槛（已确认）**：当前功能内目标FR全部已确认后才允许生成分配；后端读取精确FR版本及可选子系统目录。数量/分配条目按内容决定，不采用Mock固定数量。
- 分配结果需明确FR和子系统身份，不能仅返回无法校验的名称。
- 既有分配模型允许一个FR分配给多个子系统；页面内不可随意新建、重命名或停用子系统。是否允许Agent提出待确认的新子系统建议见Q6，未经确认不得自动创建子系统。
- 返回的是分配候选还是已保存/已确认分配、无匹配子系统时如何处理、重复生成如何避免覆盖手动结果，均待确认。

#### P-002-08：生成子系统需求图 — `FROM_SS_ASSIGNMENT_CREATE_REQ_DIAGRAM`

- **触发**：在当前功能的“FR分配”工作空间点击某个子系统，打开或激活“当前功能＋目标子系统”对应的FR分配全景视图，展示最新的子系统需求图。
- **用户目标**：全景随来源变化实时展示最新图，不是打开一次后永久保留旧图。
- **展示范围（用户纠正后已确认）**：只展示当前功能下分配到目标子系统的FR及关系，不跨功能汇总。即使同一子系统也承接其他功能的FR，本视图也不能带入那些FR。
- 后续请求、来源查询和全景身份必须能区分项目、功能、子系统；若采用结果复用，其复用范围也必须包含功能，不能仅凭子系统标识串用不同功能的图。
- **来源版本（已确认）**：子系统需求图只反映当前功能内已确认的FR分配；已保存但尚未确认的修改不进入图。已有确认版时继续展示其内容，新版显式确认后才成为图的新来源；没有已确认分配则显示空状态。
- 图的FR及分配关系以被确认分配所引用的精确版本为准，不把新的未确认分配正文或未确认FR草稿拼接进旧确认版。与现有功能视角分配表的展示关系仍待具体交互设计。
- 这是子系统需求展示入口，不自动授权增加子系统资料编辑页面。
- 图类型、结构和输出格式尚未确定，不预设为UC图、流程图或图片地址。

### 9.4 PRD串联与人工确认流程

以下是需求流程，不是已实现的HTTP状态枚举或Agent异步协议：

```text
工作台选择生成PRD → 输入提示词 → 发送
  → 后端调用 FEATURE_DEFINITION
  → 校验功能名称/描述 → 检查类似功能
      ├─ 无候选：直接创建新功能，默认确认
      └─ 有候选：暂停，等待用户确认
           ├─ 是：选定已有功能
           │    ├─ 已有PRD：报错，本次停止
           │    └─ 无PRD：继续
           └─ 不是：如名称完全相同先提示调整，再创建新功能，默认确认
  → 后端以最终function_id检查PRD单例和生成资格
  → 调用 FROM_DEFINITION_CREATE_PRD
  → 校验结果 → 保存待处理PRD → 自动打开PRD预览/编辑标签
  → 若PRD生成失败：保留新功能，重试复用功能，仅继续PRD阶段
```

**待设计约束：**

- 提示类似功能时，不提前创建新功能、不生成PRD；取消不会等同于“不是”。
- 人工确认由业务流程管理，不默认依赖Agent的`interrupt/resume`能力，也不把浏览器传来的任意候选ID当成可信授权。
- 确认回复应绑定原项目、原生成意图和原功能候选，后端重新检查可见性、操作权限及PRD是否已经存在；切换项目后不得污染新项目。
- 并发用户可能同时尝试生成PRD：查重时与写入前均需校验，最终保持每功能一个PRD；具体锁/幂等机制在正式设计中确定。
- 功能创建和Agent生成不是一个可以随意整段回滚的长数据库事务。**用户已确认**PRD生成失败后保留已创建功能，重试复用该function_id，仅重试PRD阶段，不重新调用功能定义制造重复功能；具体阶段持久化与幂等恢复机制仍待设计。
- 前端断连、重复发送和重复确认需要可查询的阶段结果及幂等语义。实际任务持久化/超时方案待设计，不承诺尚未实现的“停止即远端取消”。

### 9.5 两类图的“最新”与自动展示：保留候选方案，尚未定稿

用户本轮回复“这个先保留”。因此**来源不变复用结果、来源变化才生成**先留作候选，不记录为已确认要求，也不据此实施缓存或固定调用策略。自动展示及最新图的产品目标仍保留。以下机制继续作为后续讨论底稿：

1. 打开或激活全景时读取并核对来源版本集合；有匹配当前来源的图则直接展示。
2. 无图或来源变化时按对应scene触发生成；同一范围、同一来源快照的并发刷新合并，避免重复调用。
3. UC图建议依据当前已确认UC版本集合；未确认的草稿不混入图。没有合格来源时显示明确空状态，不调用Agent。
4. 子系统需求图的范围已明确为**当前项目＋当前功能＋目标子系统**，且**只读取已确认的FR分配及其引用版本**；已保存未确认修改不影响图。来源需记录相关FR版本、已确认分配版本，必要时包含子系统方案版本；不得跨功能复用。本项范围与版本口径已确认，缓存实现仍未定稿。
5. 页面可见期间相关来源提交成功后检测并刷新；其他协作者修改也应被发现，但推送或轮询实现、可接受延迟尚待设计，不承诺瞬时完成模型生成。
6. 新图生成期间可以保留旧图，但明确标注“旧版本/正在更新”；来源再次变化时迟到结果不得标成最新，失败也不能静默冒充最新。
7. 图是派生展示，自动生成图不得自动创建/确认UC、FR或分配。只读成员查看图的授权与后端派生结果缓存写入需单独处理，不能为看图要求用户提升为project author。
8. UC图“Agent生成图形代码、前端组件渲染”已确认；具体DSL/代码格式、组件选型、持久化和结果校验仍待正式契约。本节不批准添加图形依赖或新数据库表，也不把UC图选型自动推广为子系统需求图契约。

#### 0. 四端职责与连接边界

```text
用户 ↔ 前端 ↔ TS业务后端 ↔ 项目业务数据库
                       ↕
                    Agent服务
```

| 参与方 | 职责 | 不负责/禁止的事情 |
|---|---|---|
| 前端 | 收集输入、展示对象/图、接收用户选择，发出生成/保存草稿/确认请求 | 不直连数据库，不持有Agent Key，不把本地成功当作持久化成功 |
| 业务后端 | 验证会话、项目/功能权限、来源版本；组织Agent输入；校验结果；协调业务写入和阶段反馈 | 不把Agent输出当成可信SQL、权限或确认指令；不在等待模型/用户时持有长写事务 |
| 数据库 | 保存用户映射、项目/成员/权限、功能、对象及不可变修订、来源关系、分配和审计；执行约束 | 不因内容来自AI或人工就自动确认；不以模型输出直接覆盖已确认版本 |
| Agent | 按scene生成文本、结构化候选或图形代码并返回后端 | 本流程不设计Agent直写业务库或自行决定项目授权/确认；业务ID和关系由后端校验与维护 |

- 普通查询由后端使用`ee_project_api_ro`。业务写事务由`ee_project_api_rw`完成，事务内的必要读取也使用同一rw连接，不把一次事务拆给两个账号。
- rw不是全库管理员；新增分配/生成相关持久化如需权限增量，仍需审核迁移，不按功能、项目或scene新开账号。
- 既有本地源码事实：登录路由使用演示认证模块验证身份并签发HttpOnly Cookie，没有读取业务库密码表；不能将`ee.app_users`误说成已经实现的账号密码认证系统。项目访问时才将登录身份与业务用户/成员/权限关联。后续公司身份源不是本轮已实现内容。
- 后端发给Agent的是经授权的最小业务上下文和来源快照，不发送数据库凭据或任意全库资料。模型不替代工程师确认。

#### C. 一次PRD发送中的功能识别与用户确认

1. **前端 → 后端**：用户选择“生成PRD”并发送提示词，带当前项目及可追踪的生成意图。请求具体字段和幂等标识形式待契约设计。
2. **后端 → 数据库（ro）**：核验项目访问与本次生成资格，读取必要上下文；新建功能分支才要求功能创建权限，复用分支检查目标功能操作及PRD创建权限。不因为登录成功就允许任意生成。
3. **后端 → Agent**：第一次调用`FEATURE_DEFINITION`；Agent返回功能名称和描述给后端，后端校验结构与内容。
4. **后端 → 数据库（ro）**：只在当前项目查找类似功能。候选匹配算法尚未定；候选名称、描述及可见身份由后端返回前端。
5. **前端等待用户**：有候选展示“是否为该功能？”并接收“是/不是”；这一步不是内容版本的“确认”动作。等待期间不先创建功能、不调用PRD生成，不持有数据库长事务，也不假定Agent支持人工中断协议。
6. **前端 → 后端**：提交与原生成意图绑定的用户选择。后端重新校验项目权限、候选归属和目标功能状态，不能只信任前端传来的ID。
7. **数据库动作**：
   - 无候选或选择“不是”：同名先提示调整；rw短事务创建新功能并审计，提交后返回稳定function_id，前端在各工作空间显示同一个默认确认的新功能。
   - 选择“是”：定位已有功能，不覆盖其定义；检查是否已有PRD。存在任何PRD（空白/待处理/已确认均算）则结束本次生成并提示打开已有对象。
   - 用户取消：不继续创建或生成。
8. **后端继续**：取得最终function_id，确认没有PRD后进入D，不要求用户再点一次发送。

阶段进度和人工选择的返回/续接载荷、超时、任务持久化仍待正式设计；流程图不代表已经实现某个任务队列或恢复接口。

#### D. 生成PRD并创建待确认版本

```text

  → Agent：FROM_DEFINITION_CREATE_PRD
```
