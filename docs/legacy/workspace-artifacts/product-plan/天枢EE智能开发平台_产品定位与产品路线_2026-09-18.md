# 天枢 EE 智能开发平台：产品定位与产品路线

> 方案建议稿｜2026-09-18  
> 本文基于现有产品概念、用户提供的行业背景及三阶段路线图整理。路线为拟议目标，不表示已实现；时间从项目正式启动起计算，具体范围需结合人员、已有垂类 Agent 成熟度与试点结果确认。

# 1 产品定位

## 1.1 总体定位

**天枢是面向整车及零部件电子电器架构（EEA）研发团队、支持企业可控部署的对话式智能工程平台。**

平台以统一的 Web 工作台为入口，以中枢 Agent 负责任务协调，以垂类 Agent 执行专业工程任务，以项目数据库和知识库支撑上下文管理、成果追溯与经验复用。工程师通过自然语言描述目标、补充资料和反馈意见，即可在同一工作空间内完成工程任务的发起、专业分析、成果生成、编辑审阅及确认交付。

产品不止于提供问题答案或生成一段文本，而是将 AI 输出转化为**可编辑、可审阅、可追溯、可复用的工程成果**，逐步降低文档整理、资料检索、重复分析和跨专业协作中的事务性负担。

**一句话定位：让工程师通过对话驱动专业 Agent，在统一工作台中完成可信、可追溯的 EE 工程工作。**

## 1.2 目标客户与用户

- **目标客户：**整车企业、汽车研发机构、零部件供应商及工程技术服务团队。
- **一期核心用户：**承担产品需求定义、场景分析、功能设计与需求分配的系统工程师、需求工程师及相关架构人员。
- **后续扩展用户：**EE 架构师、功能安全工程师、信息安全工程师、软件工程师、硬件工程师、测试工程师及项目管理人员。

产品采用“统一交互入口、专业能力适配”的设计思路：不同岗位不必使用完全不同的 AI 工具，但其可用能力、输入输出模板、专业规则和数据权限必须匹配实际职责，不能为了统一界面而抹平专业差异。

## 1.3 核心价值

### （1）从反复操作工具，转向围绕工程目标开展工作

工程师说明“要完成什么”，中枢 Agent 在授权范围内组织专业能力，降低资料整理、上下文切换和重复操作成本。重要节点保留工程师确认，不以无约束自主执行替代工程判断。

### （2）从聊天回答，转向可交付工程成果

以 PRD、UC、FR、分配关系及后续专业分析成果为载体，使生成、编辑、审阅、版本与来源追溯相互衔接。AI 产物能够进入工程流程，而不是停留在不可管理的聊天记录中。

### （3）从个人经验，转向企业可复用知识

项目数据库保存业务对象、版本、来源与审阅记录；知识库沉淀经筛选和审核的模板、方法、案例及专业资料。后续项目按权限检索和复用，减少从零开始的重复梳理。知识沉淀不等于自动训练模型，也不默认允许跨客户复用数据。

### （4）从分散 AI 试用，转向安全可控的工程应用

将部署位置、模型调用、数据访问、操作权限和审计纳入企业统一管理。对于数据不得出域的场景，应采用满足要求的本地或经认可的专有环境模型方案；仅将 Web 系统部署在内网，不代表模型调用数据已经实现不出域。

### （5）与现有工具协同，而不是一开始全面替代

围绕对话式任务组织、专业 Agent 执行和工程成果管理建立差异化，并逐步接入企业已有的需求管理、建模、分析和测试工具。成熟工具已有的专业能力继续复用，平台重点减少其间的人工传递与重复处理。

## 1.4 一期产品定义与边界

**一期产品形态：Web 前端＋业务后端＋中枢 Agent＋首个需求工程垂类 Agent。**

一期建议采用“一个中枢、一个垂类、多个专业技能”的方式，优先验证完整业务闭环，而不是一次搭建多个成熟度不足的 Agent。

### 一期核心业务链路

```text
用户需求与参考资料
    ↓
PRD 生成与修订
    ↓ 工程师审阅、接受
UC 场景分析与用例生成
    ↓ 工程师审阅、接受
FR 功能设计与需求生成
    ↓
FR 子系统分配与人工确认
```

- **Web 前端：**统一工作台、项目与业务功能空间、对象标签页、对话、文档/表格/用例图展示，以及编辑和审阅操作。
- **业务后端：**对象持久化、基础权限、版本与来源关系、会话隔离、生成任务状态及必要审计。
- **中枢 Agent：**识别任务场景、组织本次上下文、调用垂类能力、管理执行状态与补充信息；不绕过业务权限和人工接受节点。
- **需求工程垂类 Agent：**通过对应技能完成提示词扩写、PRD 生成、UC 生成、FR 生成及修订。子系统分配先保证人工可搜索选择与保存，AI 分配建议按试点验证结果纳入。

业务对象沿用当前产品约定：一项目多业务功能、每功能一份 PRD；UC、FR 及分配关系拥有稳定身份和版本。对象正文、AI 会话、输入草稿与引用资料跟随当前对象工作页，不混用全局对话。

**一期边界：**聚焦需求工程试点，不承诺覆盖整个 V 模型；不在一期完成架构自动选型、完整 HARA/TARA、软硬件自动开发及全量测试验证；不以 AI 输出替代专业审查、功能安全判断或合规认证。

# 2 产品路线

## 2.1 路线原则

整体沿用原方案的三阶段、约 12 个月规划，按照：

**内部验证单领域闭环 → 国内客户验证跨专业协同 → 平台化扩展与国际化准备**

逐步推进。各阶段同时考虑业务能力、用户范围、数据基础和交付能力，不以 Agent 数量、微服务数量或接入工具数量作为主要成熟度指标。

- 一期由“概念定义与产品设计”调整为“完成概念设计并交付可实际试用的 Web MVP”。
- 二期由单一需求工程扩展到有明确输入输出关系的相邻专业场景，先选定有限场景验证，不同时铺开所有领域。
- 三期面向规模化复制和国际化试点准备，不将“第 12 个月到来”直接等同于具备国际市场全面交付能力。

## 2.2 三阶段产品路线表

> 第 1～2 月、第 3～6 月、第 7～12 月均指从项目正式启动开始的相对月份，不是自然年度月份；阶段切换以验收结果为前提。

| 维度 | 一期：第 1～2 月 | 二期：第 3～6 月 | 三期：第 7～12 月 |
|---|---|---|---|

| **产品形态与部署** | 企业内部使用的浏览器应用；采用企业认可的部署和模型访问方案，形成可操作、可保存、可回看的完整体验 | 可实施、可配置、可培训的企业级 Web 产品；提供私有化／专有环境部署方案，以及有限且明确的工具适配能力 | 平台化 Web 产品＋可配置专业能力包＋工具连接能力；支持多语言、不同部署约束和可复制交付 |
| **阶段交付物** | 可运行系统、首个垂类 Agent 接入、完整试点业务功能的需求链路、操作说明及效果评估 | 跨专业试点场景、经过验证的工具连接器、权限与部署方案、客户试点报告及交付文档 | 可复制产品版本、专业能力包、国际化适配包，以及上线、运维、评测和客户支持机制 |

## 2.3 一期实施顺序

一期范围不等于所有能力同时开发。建议分三步逐步打通：

1. **先打通底座与 PRD。** 建立项目和功能空间，接通前后端及中枢到垂类 Agent 的调用；完成扩写、PRD 生成、保存、修改与审阅。
2. **再打通 UC 与 FR。** 固定结构化输出和来源版本，支持对象标签页、全景视图，以及必要的失败重试、取消和冲突保护。
3. **最后完成分配与试点验收。** 接入正式子系统目录，完成分配关系保存，使用同一试点业务功能贯通流程，评估质量与净工时变化。

一期能否在两个月内完成，取决于现有垂类 Agent、模型、业务接口和人员条件。排期承压时，优先缩小试点功能范围和自动化深度，不以省略持久化、权限、人工确认和质量检查换取表面完整。

## 2.4 效果评价与阶段准入

产品价值以“在质量不下降前提下，工程师完成同等范围任务的净工时减少”为核心，而不是生成字数或调用次数。

建议持续评估：

- **效率：**从输入准备到审阅交付的总工时，包含 AI 资料准备、等待、审核与返工时间。
- **质量：**结构完整性、专业检查结果、人工修改量及最终接受情况。
- **追溯：**成果来源、输入版本、上下游关系与修改记录的完整性。
- **可用性：**任务成功、失败恢复、对象隔离、权限控制及结果持久化情况。
- **复用：**经授权历史资料与模板在后续项目中的使用情况和实际收益。

一期转二期前，应在内部真实任务中完成可复核的效果评估；二期转三期前，应证明产品能在有限外部客户中稳定复用和交付。未达门槛时应调整场景或方案，不按日历强行扩大市场范围。

# 3 技术路线

## 3.1 AI 平台 / 工具

> 本节在保留现有模型、工具和框架选型的基础上，对其在天枢产品中的职责、调用关系和一期边界进行补充。表中的具体选型目前属于方案假设或待验证项，不代表已经完成采购、部署、联调或效果验证。

### 3.1.1 技术路线目标

天枢一期的技术路线不是简单地将多个大模型、开发工具和 Agent 框架堆叠在一起，而是围绕一个明确目标展开：

> **让工程师在统一 Web 工作台中提出 EE 工程任务，由中枢 Agent 组织垂类 Agent 和专业技能，最终形成可审阅、可编辑、可追溯的工程成果。**

因此，技术选型需要共同支撑以下五项能力：

1. **任务理解与路由：**识别用户当前是在扩写、生成 PRD、生成 UC、生成 FR，还是进行自由分析，并选择对应的执行路径。
2. **专业能力编排：**由中枢 Agent 调度需求工程垂类 Agent，必要时按步骤调用不同技能，而不是让一个通用对话直接生成所有内容。
3. **结构化成果生成：**PRD 以 Markdown 文档承载，UC、FR 和分配关系以结构化数据承载，便于保存、校验、编辑和追溯。
4. **企业知识复用：**在用户权限范围内检索项目资料、历史成果、规范、模板和术语，避免每次任务都从空白上下文开始。
5. **可控交付：**对任务状态、输入版本、输出版本、权限、失败、取消和人工确认进行管理，避免 AI 结果直接覆盖正式工程数据。

### 3.1.3 技术分层与现有选型的职责

| 层级 | 现有选型 | 在天枢中的主要职责 | 一期使用边界 |

| AI 应用开发工具 | Aily | Skill 调试、效果验证和场景试验 | 用于早期调试或验证，正式产品能力需要沉淀到可部署的服务中 |
| Agent 框架 | LangChain / LangGraph | 工具调用、工作流编排、任务状态管理和人机中断 | 用于搭建中枢与垂类 Agent 的执行逻辑；不把框架状态等同于业务对象数据 |
| 推理框架 | vLLM | 私有化模型的推理服务和并发请求承载 | 仅在模型私有化部署路线确定后落地，需验证模型兼容、吞吐和资源使用 |
| 知识库 | RAG | 检索项目资料、规范、模板和历史工程成果 | 一期先支持受控资料检索和引用，强调项目／功能／用户权限隔离 |

### 3.1.4 中枢 Agent 与垂类 Agent 的关系

一期不把所有能力都放进中枢 Agent。建议采用“中枢负责协调、垂类负责专业执行、业务后端负责事实与权限”的分工。

#### 中枢 Agent 负责

- 识别用户意图和任务场景；
- 判断任务是快速同步执行还是长任务异步执行；
- 组装当前项目、业务功能、对象版本、附件和用户授权范围；
- 选择需求工程垂类 Agent 及其技能；
- 控制任务步骤、超时、重试、取消和人工补充信息；
- 汇总专业 Agent 的结果并交给校验层；
- 向前端反馈进度、候选产物和需要用户确认的问题。

#### 需求工程垂类 Agent 负责

- 理解 EE 需求工程的业务语义和对象结构；
- 调用 PRD、UC、FR 等专业技能；
- 按指定 Schema 生成结构化结果；
- 根据项目资料和已确认的上游版本进行分析；
- 返回假设、缺失信息、风险提示和待人工确认项。

#### 业务后端负责

- 验证用户、项目、业务功能和对象权限；
- 冻结本次任务的输入版本和来源集合；
- 保存任务、候选结果、正式版本和审阅状态；
- 校验结果是否引用了真实存在且有权限的对象；
- 处理版本冲突、幂等、审计和事件通知。

**基本原则：**Agent 可以提出内容和建议，但不能越过业务后端直接决定正式数据的所有权、权限、接受状态和版本覆盖。

### 3.1.5 一期核心调用链路

#### 场景一：提示词自动扩写

```text
用户输入一段原始需求
  → 前端调用业务后端
  → 后端以 ONE_CLICK_EXPAND 场景提交中枢
  → 中枢直达提示词扩写 Skill
  → 返回优化后的提示词候选
  → 前端只回填输入框，不自动发送、不生成 PRD
```

这个场景是短任务，不需要启动完整 Planner。扩写过程中如果用户继续修改输入，旧结果只能作为候选返回，不能覆盖用户较新的草稿。

#### 场景二：生成 PRD

```text
用户提交需求
  → 后端冻结项目、业务功能、附件和参考资料快照
  → 中枢创建异步任务并调用需求工程垂类 Agent
  → 垂类 Agent 组织需求分析、结构设计和文档生成技能
  → 返回 PRD Markdown 候选
  → 后端校验任务身份、版本和权限
  → 保存为待审阅工作版本
  → 用户编辑、审阅并接受
```

生成 PRD 的结果不应直接覆盖用户当前输入，也不应因为模型返回 completed 就自动宣布业务数据已经正式完成。

#### 场景三：生成 UC

```text
当前业务功能存在已接受的 PRD
  → 后端冻结 PRD 版本
  → 中枢调用 UC 场景分析能力
  → 垂类 Agent 输出符合 UC Schema 的结构化用例集合
  → 后端校验 12 项字段、场景结构和 PRD 来源
  → 保存候选 UC
  → 用户审阅 / 修改 / 接受
  → UC 全景视图根据已保存对象生成
```

UC 全景视图本身是业务数据的只读投影，不应额外调用模型绘图，也不能让模型自由推断未声明的关联关系。

#### 场景四：生成 FR 与分配

```text
已接受的 UC 集合
  → 中枢调用功能设计能力
  → 生成 FR 及其 UC 来源关系
  → 后端校验来源、编号、版本和重复项
  → 用户审阅并接受 FR
  → 分配页面按 FR 选择子系统
  → 后续可增加 AI 分配建议，但不能静默覆盖人工选择
```

一期优先实现人工分配的可搜索、多选和保存；AI 分配建议属于独立能力，不应和普通下拉框操作混在同一个生成任务里。

### 3.1.6 模型与技能之间的适配方式

为了避免以后替换模型时修改业务页面和业务接口，建议增加一层模型适配与能力配置：

```text
业务场景码
  → 工作流 / Skill
  → 能力配置
  → 模型适配器
  → 具体模型服务
```

例如：

| 业务场景 | 推荐执行类型 | 主要输出 | 模型关注点 |
|---|---|---|---|
| 一键扩写 | 直达 Skill | 优化后的文本 | 响应速度、语言质量、输入保真 |
| 生成 PRD | 受控工作流 | Markdown 文档 | 长文本质量、结构完整性、上下文理解 |
| 生成 UC | 结构化 Skill | UC JSON | Schema 遵循、字段完整性、来源约束 |
| 生成 FR | 结构化工作流 | FR JSON＋UC 来源关系 | 需求抽象能力、去重、可追溯关系 |
| 自由提问 | 受限 Planner | 文本或分析结果 | 工具白名单、权限范围、任务预算 |

模型本身不负责决定业务对象的编号、版本、权限和接受状态。模型生成的是候选内容，业务系统决定如何保存和展示。

### 3.1.7 知识库与 RAG 的一期边界

RAG 在一期的定位不是“把所有公司资料全部向量化”，而是先解决当前需求工程任务中最直接的资料复用问题：

- 项目需求背景和已有 PRD；
- 已接受的 UC、FR 及其来源关系；
- 经过审核的需求模板和字段说明；
- 企业内部术语、缩写和命名规则；
- 与当前任务明确相关的参考资料。

建议每条检索结果至少携带：

- 来源文档或对象 ID；
- 所属项目、业务功能和版本；
- 文档状态，例如草稿、待审阅、已接受、归档；
- 用户可见范围；
- 片段内容和定位信息。

**不能只把检索结果拼成一段没有来源的文本。** 对于法规、功能安全、信息安全和性能指标等高风险内容，AI 可以辅助整理和提示，但不能把检索命中自动表述为已经核实的工程结论。

### 3.1.8 一期必须具备的工程控制能力

为了让技术路线真正支撑产品，而不是只完成模型调用，一期建议把以下能力视为基础能力：

1. **对象级上下文隔离：**AEB 和 LKA、不同 PRD、不同 UC 标签的对话和草稿不能串用。
2. **输入快照：**生成开始时记录本次实际使用的对象版本、附件和参考资料。
3. **结构化校验：**JSON 格式正确不等于业务正确；还要校验字段、来源、权限和版本。
4. **候选与正式版本分离：**生成完成先形成候选或待审阅版本，不能直接覆盖正式接受版本。
5. **幂等与并发控制：**重复点击、网络重试或任务超时不能产生重复对象和重复版本。
6. **可恢复任务：**长任务具备查询、进度、失败、取消和必要的重试能力。
7. **人工确认：**跨阶段生成、正式接受、发布或其他高风险操作保留人工确认。
8. **可观测性：**记录任务、场景、对象、输入版本、模型／Skill 版本、耗时、错误和结果状态。
9. **安全边界：**模型和 Agent 使用的工具采用白名单，参考资料中的自然语言不能自动获得系统权限。

### 3.1.9 一期不纳入的技术范围

以下能力可以在技术路线中保留为后续演进方向，但不建议作为一期验收条件：

- 多个垂类 Agent 的大规模自由协作；
- Agent 自主写入数据库或自动接受工程成果；
- 全量工程工具的自动兼容；
- 没有权限边界的跨项目知识检索；
- 以 RAG 代替完整的数据模型、版本管理和来源关系；
- 以微服务拆分数量作为平台成熟度指标；
- 一期就覆盖完整功能安全、信息安全、架构设计、软硬件开发和测试验证流程。

### 3.1.10 本节可以放在方案中的总结段

> 天枢一期采用“Web 工作台＋业务后端＋中枢 Agent＋需求工程垂类 Agent”的总体技术路线。中枢 Agent 负责任务识别、上下文组装、能力路由和执行协调，垂类 Agent 负责 PRD、UC、FR 等需求工程任务的专业分析与成果生成，业务后端负责权限、版本、来源、任务和结果持久化。大语言模型、Agent 框架、推理框架和 RAG 共同作为可替换的技术能力层，通过统一适配和结构化契约服务于产品业务流程。技术路线的核心不是单独追求某个模型或工具，而是确保 AI 结果能够安全地进入工程工作流，并形成可审阅、可追溯、可复用的工程成果。

# 编写说明与口径提醒（可不放入正式方案正文）

1. **工时数据口径。** 用户提供的小型项目 2 万工时、中型项目 4.5 万工时，以及事务性工作占比 25%～30%，应注明为团队经验估算或待验证测算基线，不表述为已证实的全行业统计。事务性工作量不等于平台能够全部节省的工时。
2. **竞品表述口径。** 不建议用“通用 AI 无法保障安全”“传统工具无法积累知识”“某平台只能写代码”等绝对结论支撑定位。更稳妥的表述是：不同工具各有优势，本产品聚焦对话式任务组织、专业能力执行、工程对象追溯与企业可控部署的一体化体验。
3. **既有工具能力。** 截至 2026-09-18 核对的官方资料，Vector 的 PREEvision 提供需求管理和追溯能力；SystemWeaver 已发布用于工程数据问答、分析与改进建议的 WeaverAI 扩展。产品差异化不宜建立在“现有工具完全没有这些能力”这一前提上。官方资料见下方。
4. **MCP 接入边界。** MCP 可作为模型应用与工具／数据交互的标准化方式，但实际接入仍需对应工具开放能力、授权、字段映射和工程校验，不能写成“支持 MCP 即自动兼容全部工程工具”。
5. **安全与责任。** 企业内网部署、模型私有化、数据不出域、访问权限和法规合规不是同一概念，需分别规划与验证；AI 分析不能被表述为自动获得安全或合规认证。
6. **当前与规划分开。** 现有前端演示不等于真实 Agent、业务持久化或完整权限已经实现；本方案描述一期拟交付目标，不是完成情况报告。
