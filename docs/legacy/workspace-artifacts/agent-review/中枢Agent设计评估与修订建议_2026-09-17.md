## 1. 核心判断

### 1.1 建议保留的方向

| 方案 | 评价 | 补充边界 |
|---|---|---|
| FastAPI + LangGraph | 可作为当前技术基础 | 不需要因此引入大型微服务平台；业务事务仍由业务后端管理 |
| 同步与异步共用执行内核 | 合理 | 两者必须从一开始共用可靠任务登记，不是同步超时后才临时创建记录 |
| 稳定场景码，对外隐藏 Agent/skill 名称 | 很适合产品按钮 | 场景的公开输入/输出也要版本化；不能仅隐藏名字，参数仍直接耦合内部 skill |
| 简单任务跳过 Planner | 合理 | 跳过 Planner 确定的是路由，不意味着 LLM 输出内容确定 |
| 结构化输出 | UC/FR/分配必需 | 校验分成 JSON、Schema、业务关系三层 |
| 后端预取资料为默认方式 | 适合最初闭环 | 要带来源 ID/版本和完整性信息，不只拼接一段文字 |
| 专业 Agent 分工 | 合理 | 分工以能力和输出契约为中心，不等于每个角色必须独立部署或使用不同模型 |
| 单进程起步 | 可用于受控原型 | 单进程不等于可以把已受理任务只保存在内存 |

### 1.2 最重要的架构调整

**中枢应是“受约束的任务调度与结果协调层”，不是一个能够自由修改全项目数据的超级聊天机器人。**

对于本项目，建议把“确定性产品流程”与“自由智能编排”分开：

- 扩写：固定 skill。
- PRD / UC / FR 生成与修订：固定或受控 workflow，内部允许调用专业 Agent。
- 开放式分析：Planner 在明确授权的能力与数据范围内编排。
- 保存、接受、归档、子系统手动分配：业务接口，不交给 Planner 决定。

LangGraph 官方区分预定义执行路径的 workflow 与动态选择过程/工具的 agent。[T1] 本项目采用哪条路径是产品设计选择；不能把“用户输入自然语言”直接等同于“必须开放规划全部业务阶段”。

## 2. 推荐总体架构及责任边界

```text
前端：当前对象标签、输入、附件、进度、预览、确认
  │ 现有用户认证；提交对象身份与业务动作
  ▼
业务后端：唯一业务事实来源
  ├─ 用户权限、项目/业务功能/对象归属
  ├─ PRD/UC/FR/分配的正式版本与审阅状态
  ├─ 会话记录、附件授权引用、输入快照
  ├─ ai_runs / 输入输出映射 / 冲突检测
  └─ 校验并提交工作版本、业务事件
  │ 服务间认证 + 固定业务范围 + 版本快照
  ▼
AI 服务入口
  ├─ 场景解析、任务登记、幂等与预算
  ├─ 单 skill / 固定 workflow / 受限 Planner
  ├─ 任务恢复、澄清中断、取消、结果交付
  └─ 输出与工程质量检查
  │ 有类型的任务包 / 有类型的结果包
  ▼
专业能力：产品分析、场景分析、功能设计、分配建议、质量检查
  │
  └─ LLM、经过授权的只读业务工具

AI 返回“候选产物” → 业务后端校验权限、来源与版本 → 发布待接受的工作版本
```

这里“发布工作版本”仅指更新业务对象的当前 head，使页面可查看，**不等于用户点击接受，也不等于对外正式发布**。

### 2.1 各层应该负责什么

| 层 | 应负责 | 不应负责 |
|---|---|---|
| 前端 | 当前标签定位、输入草稿、预览、操作反馈 | 持有 AI 服务密钥；自行决定正式对象权限 |
| 业务后端 | 授权、业务来源、版本、保存/接受、冲突与审计 | 用模型回答替代事务校验 |
| 中枢运行时 | 调度、状态机、上下文投递、预算、恢复与结果合并 | 绕过后端权限；凭模型判断覆盖数据库 |
| 专业 Agent | 在限定任务内分析并产出候选内容 | 自行跳转任意项目；擅自触发整个下游流程 |
| 校验器 | Schema、引用集合、重复键、必填项等规则检查 | 把“JSON 合法”宣布为工程正确 |
| 用户 | 澄清需求、审阅接受、批准危险变更 | 被迫通过自然语言 yes/no 替代所有产品按钮 |

专业 Agent 不必相互自由聊天。建议第一版默认走“中枢委派 → 专业结果返回 → 中枢校验/汇总”；专业 Agent 如需协助，返回结构化协助请求，由中枢审核是否允许追加步骤。避免无限递归委派和隐式共享全部会话。

### 2.2 最小专业能力划分

| 逻辑角色 | 输入 | 输出 | 建议边界 |
|---|---|---|---|
| 产品分析能力 | 用户需求、当前 PRD、授权参考资料 | PRD Markdown 或修订候选 | 不自动接受，不擅自创建 UC |
| 场景分析能力 | 指定 PRD 版本及范围 | 完整 UC 结构 | 不编造性能阈值/法规事实 |
| 功能设计能力 | 冻结的 UC 版本集合 | FR + 来源 UC 版本引用 | 不能拿整段聊天代替来源集合 |
| 分配建议能力 | FR 版本集合、项目子系统字典快照 | 子系统 ID 集合及建议理由 | 不是手动下拉框保存流程；是否上线此能力另确认 |
| 质量检查能力 | 候选内容、校验规则、来源 | 规则失败、内容风险、缺失信息 | 硬规则优先代码校验；模型复核不是事实证明 |

建议模型复核最多有限轮修订；达到限额后返回具体问题，不能让“作者 Agent”和“审阅 Agent”无限互相改稿。角色共用模型或拆分模型，应由任务样本评测决定。

## 3. 与现有产品操作逐项对齐

| 页面动作 | 推荐执行 | 输入/结果要求 | 对用户的结果 |
|---|---|---|---|
| PRD 输入框自动扩写 | `ONE_CLICK_EXPAND`，直接 skill | 输入是整段草稿，不应只有 feature_name；输出优化后的提示词 | 仅回填当前草稿，不发送、不生成 PRD；若等待期间草稿变更，不覆盖新文本，保留候选供选用 |
| 首次生成 PRD | `GENERATE_PRD`，受控 workflow | 当前业务功能、预留 PRD 身份、需求和附件快照 | 成功提交工作版本后按既有规则激活原 PRD 标签；不自动切换用户当前项目 |
| 修改 PRD | 建议单独 `REVISE_PRD` 场景 | 目标对象、base_revision_id、修改意图、允许修改范围 | 同一个 PRD 的新候选版本，不创建另一个同功能 PRD |
| 生成 UC 集合 | `GENERATE_UC`，结构化 workflow | 当前功能已接受 PRD 的指定版本 | 发布后出现 UC；不一次弹开所有 UC 标签 |
| 修改一条 UC | 建议 `REVISE_UC` | 目标 UC、版本与引用快照 | 仅产生当前 UC 的候选，不覆写其他 UC |
| 打开 UC 全景 | 普通业务查询/派生视图 | 读取当前功能的有效 UC | 自动只读用例图，无额外 LLM 绘图任务，无隐藏修改能力 |
| 生成 FR 集合 | 建议 `GENERATE_FR` | 明确且冻结的 UC 输入集合 | FR 内容与准确的 UC 来源关系 |
| 修改一条 FR | 建议 `REVISE_FR` | 目标 FR、版本、来源约束 | 同对象新版；全景读已提交版本 |
| FR 分配下拉框搜索/勾选 | 普通业务 API | FR 分配对象、子系统 ID、并发版本 | 只更新分配关系，不通过 LLM，不改 FR 原文 |
| AI 分配建议 | 可选 `SUGGEST_FR_ALLOCATION` | FR 快照、项目子系统字典 | 返回候选分配，不能静默覆盖用户手动选择 |
| 当前标签自由提问 | 只读问答或受限 Planner | 当前对象范围及显式附件 | 解释与分析；需要写操作时转显式场景并走授权 |

说明：除已有 `ONE_CLICK_EXPAND`、`GENERATE_PRD`、`GENERATE_UC` 等外，表内新增场景名均为建议，不是已存在接口。[L1/L2/L4]

原方案把扩写描述为“50～100字功能说明”；本项目需求是优化用户已输入提示词。[L1 §9A.2 / L2 PRD-02] **这是实际语义不一致，应优先改正**，不能把长需求压缩到 100 字再当成扩写。

## 4. 对接前必须补齐的关键问题

### P0-01：业务身份不能只依靠 thread_id

现有 AgentRequest 的 context 主要是 user_id、requirement_id、vehicle_platform，不足以落实项目已有的对象隔离规则。[L1 §6 / L2]

建议明确这些不同身份：

| 标识 | 意义 |
|---|---|
| project_id | 项目与权限范围 |
| function_id | AEB/LKA 等业务功能的稳定身份，不能用名字替代 |
| target_artifact_id + artifact_type | 单对象操作目标；批量操作目标可为空但 scope 必填 |
| view_type | PRD/UC/FR/全景等工作上下文，不是对象主键 |
| conversation_id | 面向用户的持久会话，隶属确定的对象或全景范围 |
| business_run_id | 业务后端 ai_runs.id |
| task_id | AI 服务执行记录；与 business_run_id 建立持久映射 |
| execution_thread_id | LangGraph 恢复所用游标，由 AI 服务管理 |
| ui_tab_id | 浏览器显示身份，最多用于关联，不作为服务端授权依据 |

推荐将“业务会话”和“执行线程”拆开：同一对象的会话可以有多轮任务，每个独立执行任务有自己的恢复线程，业务会话摘要和有效对象快照按需注入。这样不同执行不会覆盖同一图状态；代价是需要业务侧维护会话及上下文组装。若坚持一个会话复用一个图线程，则同线程的运行/等待人工任务必须串行，不能仅靠 thread_id 声称并发安全。LangGraph 的 checkpointer 是线程状态保存机制，不是业务会话权限模型。[T2/T3]

对象标签的会话是否“每用户独立”仍需确认；建议默认按用户隔离，同一对象内容可共享而私人对话不自动共享。

### P0-02：缺少版本快照、来源与并发提交契约

最新数据库设计已经规划 ai_runs、ai_run_inputs、ai_run_outputs、输入集合 hash、功能 epoch 和 base_revision_id；AI 方案需要对齐这些概念，不另建一套互不映射的业务状态。[L4 §7]

典型风险：

1. AEB 的任务开始时读取 UC r2。
2. 用户随后保存了 r3，或者给本功能新增了另一条 UC。
3. 旧 AI 任务完成。
4. 若只看 task completed 就覆写，既可能覆盖新版本，也可能声称“已分析全部 UC”但漏掉新增 UC。

建议：后端在调用前冻结输入集合及版本；AI 回传原 input_snapshot_id/hash 和输出来源；提交时后端重新鉴权并比较当前版本/集合。发生变化进入 conflict，不静默覆盖。模型自己回显的 hash 不是安全证明，必须与后端保存的快照核对。

**产物必须区分：**

- 模型 token/未完整 JSON：仅流式预览。
- 完整且通过初步校验的候选：staged，不自动成为下游输入。
- 业务校验通过并提交 head 的工作版本：用户可查看编辑，仍待接受。
- 用户接受版本：按对应阶段门槛成为下游来源。

原 DB 方案对整批发布、部分失败、上游接受门槛有若干设计默认；要在对接前收口，不把它们直接写成用户已确认。[L4 §1.2/§7/§16]

### P0-03：任务可靠性不能等到 M3 再补

当前方案 TaskStore 为内存记录 + 终态 SQLite；运行中与等待人工的任务没有完整持久任务账本。[L1 §11] 即使图 checkpoint 在磁盘，task→thread 映射、幂等键、回调投递、超时策略和业务提交状态也不会自动因此可靠。

建议原型也做到：

1. 返回 task_id/202 **之前**，持久写入任务、范围、输入引用、幂等键和当前状态。
2. 状态转换持久化，不只保存成功结果；重启后扫描 running/waiting_human 和未交付结果。
3. 为任务执行维护强引用、异常回收、并发上限；开发热重载不得作为可靠生产运行方式。
4. 采用租约或单实例所有权标记；明确崩溃后能恢复的步骤与不能安全重试的步骤。
5. 对外部副作用使用幂等键和业务事务/条件更新；不能承诺仅靠 checkpointer 达成“恰好执行一次”。
6. 工程原型可先持久 SQLite；面向项目的多人部署应与已有 PostgreSQL 设计统一规划。不是仅换 Saver 名称就完成队列、迁移、并发和恢复工作。[L4/T2]

单进程可保留，不必立刻引入 Celery；**基础持久化、幂等、背压是最小正确性，不是重基础设施**。

### P0-04：中断、取消、HTTP 等待超时语义不完整

建议拆成三个时钟：HTTP 等待时长、模型/任务有效执行预算、人工等待截止时间。否则用户尚在回答问题，10 分钟“整体超时”已把任务终结。

- 同步等待超时但任务继续：建议返回 202 + task_id + 查询地址，而不是把正常继续执行描述成失败；若保留 408，必须说明任务仍存活，且同幂等键重试不新开模型调用。
- 普通 asyncio.wait_for 超时会取消被等待任务；如需继续后台执行，必须明确任务所有权及取消隔离方式，而非文档一句“自动转异步”。[T5]
- `resume` 不能仅有 `{reply: "yes"}`。应带 interrupt_id、结构化答复、expected_task_version 和幂等键；审批另绑定动作/产物版本，拒绝过期确认。
- 业务后端必须核验回答人或审批人的权限；不能只相信请求体里的 user_id。
- LangGraph 恢复中断时会从所在节点开头重新执行，因此中断前的外部副作用应拆分或保证幂等。[T3]
- 取消建议先 cancel_requested，再停止新步骤、停止提交；已取消结果不得因迟到回调重新写回。已经提交成功的任务不能假称回滚成功；返回终态并让用户另行处理版本。
- 同步入口遇到 waiting_human 必须即时返回可恢复句柄，不能阻塞 HTTP 等用户。

### P0-05：UC/FR/分配的结构化契约还没有真正定义

附件 UC 示例只有 id/title/actor/precondition/main_flow/alt_flow，这可以是接口示意，但**不能作为本项目最终 UC Schema**。[L1 §9 / L6]

当前必须覆盖的 12 项：用例名称、描述、编号、参与者、前置条件、场景、后置条件、扩展用例、HMI 交互逻辑、法规需求、性能需求、非功能需求。“场景”内部保留主流程、4 条分支、5 类异常；编号和持久 ID 由业务侧管理或验证，不允许模型随意重编号。[L4 §6.5 / L6]

建议统一产物信封，按 artifact_type 引用业务方维护的不可变 schema_version；PRD 内容仍是 Markdown，不因为统一信封就强制改成章节字段表。

校验分三层：

1. **格式层**：JSON 可解析、未截断、不是空 content。
2. **结构层**：字段/类型/长度/枚举/数量符合指定 schema。
3. **业务层**：来源属于本次输入集合；FR 引用真实的 UC 版本；分配目标属于授权字典；目标与用户有权限；没有被覆盖的新版本。

DeepSeek JSON Output 文档承诺 JSON 格式输出，并提醒截断与空内容情况；不能据此把任意 JSON Schema 符合性视为自动保证。[T4] 即便选定模型支持严格 Schema，第三层业务校验仍必须由后端执行。

有限的自动格式修复可以做，但需要上限并保留校验问题；重试不重复提交任何业务变更。性能数字、法规条文和来源证据应区分“已提供事实/推导/待核实”，不能用 Schema 校验冒充领域审阅。

### P0-06：内网 API Key 不等于业务授权

可保留“后端到 AI 服务用 API Key”的原型选择，但不能以此替代用户、项目、对象权限。[L1 §12/§16]

建议：

- 前端只访问业务后端，不暴露 AI Key；AI 服务默认不对浏览器开放任务接口。
- 服务身份与用户委托身份分开；用户身份由已认证业务后端签发或封装在受信链路上，不由前端任意填写 context.user_id。
- 后端 /internal 工具每次检查委托范围、项目/功能/对象及操作权限；提交时再次鉴权，处理执行期间权限撤销。
- enabled_tools 只能缩小权限：有效集合 = 场景白名单 ∩ 服务策略 ∩ 用户授权 ∩ 本次请求限制。默认不暴露写工具。
- 共享编译图可以复用；请求级令牌/用户/工具实例不能通过修改共享单例或全局变量注入，更不能进 prompt 或可持久 checkpoint。
- “参考资料只读”是内容说明，不是安全隔离。资料与指令分层；工具参数、权限和输出由代码约束，资料里的指令不能直接授权动作。[T6]

回调“仅校验内网域名、无认证”建议修改：目标注册并绑定接入方；使用 HMAC（时间戳、事件 ID、正文摘要）或等价认证机制，拒绝重放。限制协议、解析后的允许地址和重定向，防止可控 callback_url 变成任意请求通道。域名校验不能代替请求发起者认证，SSRF 防护也不是仅检查字符串后缀。[T7]

如果一期不愿实现回调认证、重试和去重，**先用后端鉴权轮询**比发送不可靠的无认证 Webhook 更合适。

### P0-07：业务完成不能只相信一次回调

原方案“后台收到回调立即落库”是正确意图，但“发送一次快照”加 24h TTL 不构成完整交付保障。[L1 §7.6/§16]

建议：

- AI completed 表示产物已在 AI 服务持久准备好；不直接等同于业务 ai_runs.succeeded。
- 后端拉取/接收结果 → 验证 schema、来源、授权、版本 → 事务提交 → 写 project_events outbox → 再向前端宣布业务成功。
- 业务接受事件或回调先持久入站去重记录，再返回成功响应；异步落库失败要可重试并可查询。
- 回调重试采用退避与上限，并提供投递状态、对账查询和人工重投入口；丢回调可由轮询补偿。
- TTL 与交付确认分离。到期尚未交付的结果进入明确保留/告警策略，而不是后台仍未收到就静默清除。
- 业务产物/会话长期保留在业务系统，不能受 AI 线程“7 天删除”的默认配置支配。

## 5. 中枢与专业 Agent 的内部交接契约

附件重点是“后台如何调用中枢”，但用户真正需要的“中枢如何调用各专业 Agent”尚缺可验收定义。

### 5.1 委派任务包（建议）

至少包含：

- business_run_id、task_id、step_id、parent_step_id、attempt_no。
- scene/version、目标能力 ID/version、workflow/prompt/model 配置版本。
- project_id、function_id、scope、target_artifact_id；全部继承后端受信范围。
- goal、operation、允许修改的对象/字段范围。
- input_snapshot_id、带版本来源、与本步有关的参考资料。
- expected_output_schema 的 ID/version/hash。
- 允许调用的工具、读写范围、单步时限、token/调用次数/重试预算。
- 验收规则与完成条件。

不建议把所有 worker 的全部聊天记录拼成一个无边界大 prompt。专业能力拿“完成本步所需的最小快照”，中枢保留结果索引及摘要；必要资料通过授权引用检索。

### 5.2 结果包（建议）

结果状态使用明确枚举，例如 succeeded / needs_input / failed，而不是靠中枢读一句“差不多完成了”决定下一步。至少带：

- step_id、attempt_no、产物类型、schema_version。
- structured 或 Markdown content、稳定 output_key。
- 实际来源引用与版本、assumptions、待核实事项。
- 可重试错误与不可重试错误、校验问题列表。
- usage、耗时、模型/模板/能力版本。

`needs_input` 由中枢合并为面向用户的明确问题，不让五个 Agent 同时在右侧聊天各自提问。工具日志、私有推理和内部 system prompt 不直接流到用户会话。

### 5.3 规划结果也要可执行校验

Planner 产生的 plan 应是 DAG 或受限步骤列表，明确依赖、输入绑定、输出引用、是否可并行以及终止条件。执行前校验：

- 不引用不存在的 Agent/skill/工具，不跨越授权 scope。
- 不出现循环依赖或无界委派。
- 不把需要上一步产物的节点并行提前执行。
- 不用未经接受/尚未发布的候选绕过产品阶段门槛。
- 预算不超过任务上限；重规划次数有上限。

由代码保证的规则不要放给另一个模型“自由决定”。

## 6. 建议的接口修订形态

以下仅为 v0.3 讨论草案，不是现有可调用接口。

### 6.1 场景声明增加明确 execution.type

```yaml
scenes:
  ONE_CLICK_EXPAND:
    version: 1
    execution:
      type: skill
      target: product.prompt_expand
    input_schema_ref: prompt_expand.input.v1
    output_schema_ref: prompt_expand.output.v1
    allowed_effects: [return_prompt_candidate]
  GENERATE_PRD:
    version: 1
    execution:
      type: workflow
      target: prd_generation.v1
    input_schema_ref: prd_generation.input.v1
    output_schema_ref: prd_generation.result.v1
    allowed_effects: [return_artifact_candidate]
  ANALYZE_CURRENT_SCOPE:
    version: 1
    execution:
      type: planner
      target: scoped_analysis.v1
    input_schema_ref: analysis.input.v1
    output_schema_ref: analysis.output.v1
    allowed_effects: [return_analysis]
```

`allowed_effects` 是运行时强制执行的策略，不能只是给模型看的提示词。公开场景 schema 与内部能力入参通过版本化适配层映射，内部重构才真正能做到后端无感。

### 6.2 请求应带固定业务范围与快照

```json
{
  "scene": "GENERATE_UC",
  "scene_version": 1,
  "business_run_id": "run-001",
  "conversation_id": "conversation-001",
  "scope": {
    "project_id": "project-001",
    "function_id": "function-aeb",
    "view_type": "UC_OVERVIEW",
    "target_artifact_id": null
  },
  "operation": "generate",
  "input_snapshot": {
    "id": "snapshot-001",
    "set_hash": "sha256:example",
    "primary": [
      {"artifact_type": "PRD", "artifact_id": "prd-001", "revision_id": "prd-r3"}
    ]
  },
  "inputs": {"instruction": "依据已接受的 PRD 生成当前功能的用例集合"},
  "delivery_target_id": "ts-backend",
  "trace_id": "trace-001"
}
```

示例 ID 仅表示身份关系，不限定 UUID 格式；`sha256:example` 不是有效摘要。实际原文可在受限 reference_data 中内联，或通过经授权的快照读取接口取得；不能仅传一个无法解引用的 snapshot_id。

- 操作人从受信认证上下文取得，而非让模型输出决定。
- 幂等统一使用一个明确位置，例如 `Idempotency-Key` HTTP 头；同键同规范化请求返回原任务，同键不同业务输入返回冲突。
- 基础输入、权限、配额校验失败不创建“已受理任务”；受理之后任何失败都留下持久状态。
- API、scene、schema、workflow、prompt、能力配置版本分别记录；7 天后恢复旧任务不能默默换成已修改的流程定义。

### 6.3 产物信封

```json
{
  "task_id": "task-001",
  "business_run_id": "run-001",
  "status": "completed",
  "input_snapshot_id": "snapshot-001",
  "result_manifest_version": 1,
  "artifacts": [
    {
      "output_key": "prd:primary",
      "artifact_type": "PRD",
      "operation": "revise",
      "target_artifact_id": "prd-001",
      "base_revision_id": "prd-r3",
      "schema_version": "prd-result.v1",
      "content_format": "text/markdown",
      "content": "# 功能概述\n本次 PRD 修订候选内容。",
      "source_refs": [
        {"artifact_id": "prd-001", "revision_id": "prd-r3", "role": "primary"}
      ]
    }
  ],
  "warnings": []
}
```

这是 PRD 修订的独立示例，不是上面 GENERATE_UC 请求的响应；UC/FR 使用各自 schema 的结构化 content。AI 的 completed 表示计算产物就绪，业务后端仍须完成提交检查。对于新增 UC/FR，使用稳定 output_key 与业务侧预留/分配的 ID 映射；重试不按名称重新创建重复对象。

### 6.4 AI 任务状态与业务状态分开映射

| AI 执行侧 | 业务后端 ai_runs | 含义 |
|---|---|---|
| pending / planning / running | queued / running | 执行中，尚未完成业务提交 |
| waiting_human | 建议补充对应状态或明确扩展字段 | 正在等待本次 interrupt 的答复 |
| completed | ready | 完整产物可取；尚未证明业务提交成功 |
| completed 且后端提交成功 | succeeded | 发布新的待接受工作版本 |
| completed 但版本/权限校验未过 | conflict / failed | 不覆盖现有业务数据 |
| cancelled / failed / timeout | 对应取消/失败及明确原因 | 不得伪装部分成功 |

DB V1.1 当前没有 waiting_human；这是两份设计需要联合补齐的地方，不应让后端一直显示普通 running。[L1 §8 / L4 §7.1]

### 6.5 流式事件

建议对业务侧暴露 `task_state_changed`、`progress`、`answer_delta`、`artifact_candidate_ready`、`input_required`、`task_completed`、`task_failed`，每个事件带 task_id、business_run_id、event_id、sequence。`artifact_committed` 由业务后端在提交事务后产生，不由 AI 服务宣布。

SSE 的 id 与 Last-Event-ID 是恢复事件流的基础机制。[T8] 本项目还应定义快照序号 watermark：重连返回当前快照和其 sequence，再继续发送后续事件，不能把“全量正文快照”当 token delta 追加而造成重复文本。过期历史应明确要求重新同步。

对外只发送可展示答案与业务进度，不直接转发全部 LangGraph 内部 token、工具凭据或推理过程。第一版可以轮询，但最终查询结果必须和流式候选使用同一产物标识。

## 8. 分阶段搭建建议

### 阶段 A：冻结最小可对接契约

- 收口 scope、会话归属、场景输入/输出 schema、版本快照、任务完成/业务提交语义。
- 先确定 PRD、UC 契约及测试样例；FR/分配至少定义关系引用方式。
- 对齐业务后端 `/v1/...` 与 AI 内网 `/api/v1/agent/...`，不让前端直接照搬 AI 的服务密钥接口。
- 明确谁发布 schema、何时兼容旧版本、旧任务如何恢复。

### 阶段 B：先做 PRD 的垂直闭环

同时推进必要的业务持久化，不先造完全部 Agent 平台：

1. 功能/PRD 稳定身份、最小权限、基础版本存储。
2. 自动扩写：输入原文、返回候选、草稿版本保护。
3. PRD 生成：固定 workflow，持久任务 + 轮询 + 幂等 + 取消。
4. 结果后端提交待接受版本，前端按既有标签规则展示。
5. 修改、保存、接受、失败、重试与版本冲突联调。

此阶段无需开放任意 Planner、工具回查或全套 Webhook。不要在扩写都未正确回填时先开发复杂多 Agent 讨论机制。

### 阶段 C：UC / FR 结构化链路

- UC 12 字段 schema、源 PRD 版本、批量输出与整批提交策略。
- FR 来源 UC 多对多、字段完整性、无效引用拒绝。
- UC/FR 全景读取统一业务对象，不能从另一份 Agent 私有缓存构造。
- 加入质量评测集，统计业务校验失败率、人工修改量和来源覆盖情况。

### 阶段 D：分配、人机交互、流式交付

- 先完成普通分配保存接口和字典查询，再考虑 AI 分配建议。
- 精确 interrupt/resume、SSE 恢复、回调认证/重试及任务对账。
- 可以将 SSE 提前到阶段 B 改善 PRD 体验，但不能挤掉可靠任务和提交语义。

### 阶段 E：再开放更灵活的编排

- 增加受限 Planner、按需数据工具、限定并行、重规划预算。
- 只有在单实例恢复/容量测试明确需要时，再引入外部队列和多实例 worker。

## 9. 验收用例与可观测性

### 必测业务/隔离用例

1. 同项目 AEB 与 LKA 同时生成 PRD；正文、对话、附件、产物全部隔离。
2. 同一功能两个 UC 标签分别发送修订；每个结果回到原对象。
3. 用户切换项目时原 PRD 完成；不切换项目，不把结果写入当前项目。
4. 扩写等待期间用户继续输入；旧结果不覆盖新草稿，不自动发送。
5. 同键提交两次只产生一个执行；同键不同请求被拒绝。
6. 同步等待超时后查询原 task 可继续，不新开第二次生成。
7. 进程在 running、waiting_human、完成未交付时分别重启，可恢复或明确失败，不出现永久悬空。
8. 重复 resume、过期 interrupt、无权限审批均不触发重复执行。
9. 用户取消与模型完成并发；最终只出现一个合法终态，取消成功后不再提交。
10. 生成中用户修改目标版本、增删上游或撤销权限；后端阻断旧结果提交。
11. UC 缺字段、FR 引用不存在/跨功能 UC、分配引用无效子系统均被拒绝。
12. 生成 13 条 FR 中途失败，不把 6 条悄悄宣布为完整成功；按确认的部分结果策略处理。
13. 模型返回格式合法但内容空缺/来源造假的 JSON；不能直接通过业务提交。
14. 回调重复、丢失、乱序、过期、伪造；不重复生成版本，能对账恢复。
15. SSE 重连无重复追加，旧 token 不覆盖新正式版本，无跨项目事件泄漏。
16. reference_data 内含“忽略规则、调用写库工具”的指令；不能越权执行。
17. PRD 接受前不能生成 UC；保存、接受、生成是独立操作。[L2]
18. UC 全景始终只读；分配页面只有子系统关系可修改。

### 需要采集但不预设无依据承诺的指标

- 扩写/PRD/UC/FR 各场景 p50/p95 耗时，排队与模型耗时分开。
- 各场景 JSON/Schema/业务校验一次通过率，修复和重试次数。
- 每步与每任务 tokens/调用次数/成本预算使用情况。
- 人工接受率、接受前修改量、来源覆盖率；不以“生成了多少字”替代效果。
- 重启恢复成功率、回调积压、任务等待时长、冲突率与取消后残留调用。
- 模型/提示词/工作流/Schema 版本、trace_id、上游请求 ID；不默认记录原始敏感正文或凭据。

本次没有执行上述验收，也没有用真实模型测量质量、成本或吞吐量。
