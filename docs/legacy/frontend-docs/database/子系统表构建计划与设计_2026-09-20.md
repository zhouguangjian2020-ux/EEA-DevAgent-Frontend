## 1. 本阶段目标

本阶段先完成项目级“子系统字典”的数据契约、源数据清洗规则、表结构、导入校验和回滚方案，为后续 FR 分配提供稳定的子系统 ID。

本阶段不做以下事情：

- 不创建业务数据库、schema、角色或表；
- 不把 Excel 直接导入生产表；
- 不把“关联主功能”误认为当前项目的 AEB/LKA `business_functions`；
- 不在 `subsystems` 表中加入用户、角色、`can_edit` 等权限字段；
- 不因为 Excel 里出现 `/` 就创建名为 `/` 的主功能。

## 2. V1.1 权限设计核对结论

V1.1 已包含权限设计，位置如下：

- 第 13.5 节：权限选型、能力点、角色、范围绑定和授权审计；
- `permission_definitions`：页面/动作能力点，例如 `page.allocation.open`、`allocation.read`、`allocation.update`、`allocation.generate`、`allocation.accept`、`allocation.archive`；
- `access_roles`、`role_permissions`：角色及其能力集合；
- `access_bindings`：项目、业务功能、业务对象三级授权范围；
- `security_audit_events`：赋权、撤权、角色变更和敏感操作审计；
- 权限计算规则：对象绑定 > 功能绑定 > 项目绑定；上级 `no_access` 和页面入口权限不能被对象授权绕过。

子系统字典是**项目级共享数据**。V1.1 的归属范围矩阵已将 `subsystems` 放在项目范围，FR 分配通过 `allocation_targets` 引用它。建议保持以下边界：

| 对象 | 负责什么 | 是否放在 `subsystems` |
|---|---|---:|
| 子系统目录 | SS 编号、名称、域、描述、启停、目录版本 | 是 |
| FR 与子系统关系 | 某个 FR 分配版本选择了哪些子系统 | 否，使用 `allocation_targets` |
| 用户能否查看/修改分配 | 页面能力、对象操作、范围授权 | 否，使用五张权限底座表 |
| 子系统自身的管理员维护权限 | 目录管理能力，例如 `subsystem.manage` | 否，注册到 `permission_definitions` 并由 `access_bindings` 授权 |
| AEB/LKA 业务功能 | 产品工程中的业务功能实体 | 否，使用 `business_functions` |

因此，本次建库时即使先只创建 `subsystems`，也必须预留权限接口：所有子系统目录 API 都要按 `project_id` 校验项目成员、页面能力和目录管理能力；不能用“知道 SS 编号”代替授权。

### 3.2 合并单元格处理规则

Excel 的“域”列使用纵向合并。合并区域的值只存放在首行，不能按普通逐行读取，否则后续行的域会被误读为空。

导入预处理必须执行以下规则：

1. 读取每个合并区域的左上角值；
2. 将该值向下展开到该合并区域覆盖的每一条数据行；
3. 将展开后的 `domain_name` 和 `domain_code` 写入 staging；
4. 保留 `source_row` 和 `source_domain_raw`，便于追溯原始 Excel；
5. 不能把 Excel 合并效果直接当成数据库中的一条记录。

展开后各域数量如下：

| 域 | 条数 |
|---|---:|
| 车身（1XX） | 12 |
| 底盘（2XX） | 6 |
| 信息娱乐（3XX） | 14 |
| 动力（4XX） | 4 |
| 热管理（4XX） | 1 |
| 自动驾驶（5XX） | 3 |
| 车辆模式（7XX） | 1 |
| SOA（8XX） | 2 |
| 合计 | 43 |

注意：“动力（4XX）”与“热管理（4XX）”虽然共享数字段后缀，但在源数据中是两个不同的域，不能仅按 `4XX` 合并成一类。建议域使用稳定的内部 ID，显示名称和源编号分开保存。

## 4. 推荐的数据模型

### 4.1 最小正式表：`subsystems`

`subsystems` 是项目内共享的正式子系统目录。它不归属于某一个 AEB/LKA 业务功能；同一项目内的多个业务功能可以共同引用同一个子系统。

| 字段 | 类型 | 约束/默认值 | 说明 |
|---|---|---|---|
| `id` | `uuid` | PK | 子系统稳定身份；被 `allocation_targets` 引用后不能因改名而改变 |
| `project_id` | `uuid` | NOT NULL，FK `projects` | 项目隔离键 |
| `domain_id` | `uuid` | NOT NULL，FK `subsystem_domains` | 域的稳定引用 |
| `code` | `text` | NOT NULL；UQ(`project_id`,`code`) | 如 `SS101`，保留源编号 |
| `name` | `text` | NOT NULL | 如“外灯控制系统” |
| `description` | `text` | NOT NULL | Excel 多行描述原文；不拆成伪字段 |
| `enabled` | `boolean` | NOT NULL DEFAULT `true` | 新分配是否可选；历史分配不删除 |
| `catalog_version` | `integer` | NOT NULL，初始 `1` | 项目目录版本；目录变更递增 |
| `source_kind` | `text` | CHECK(`excel`/`manual`/`migration`/`ai`) | 初始数据为 `excel` |
| `source_ref` | `text` | NULL | 例如文件名、sheet 与行号的组合，不放完整文件内容 |
| `metadata` | `jsonb` | NOT NULL DEFAULT `'{}'` | 仅存非关键扩展，不能藏关系和权限 |
| `created_at` | `timestamptz` | NOT NULL | UTC 写入 |
| `updated_at` | `timestamptz` | NOT NULL | UTC 写入 |
| `created_by` | `uuid` | NULL/FK `app_users` | 系统导入可为空或使用迁移主体，按审计规则确定 |
| `updated_by` | `uuid` | NULL/FK `app_users` | 最近修改人 |
| `archived_at` | `timestamptz` | NULL | 目录项归档时间；不物理删除 |

### 4.2 建议新增的支持表：`subsystem_domains`

纠正：V1.1 的 `subsystems` 原字段中尚无 domain 字段或域表；这是初稿根据 Excel 新提出的扩展。由于源 Excel 有合并域、同一数字段后缀对应两个不同域，建议在正式导入前增加一张小字典表：

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | `uuid` | PK |
| `code` | `text` | 项目内或全局唯一；建议 `BODY_1XX`、`CHASSIS_2XX` 等稳定编码 |
| `source_code` | `text` | 如 `1XX`、`2XX`、`4XX`、`5XX`、`7XX`、`8XX` |
| `name` | `text` | 如“车身”“动力”“热管理” |
| `display_name` | `text` | 如“车身（1XX）” |
| `sort_order` | `integer` | 按源表出现顺序 |
| `enabled` | `boolean` | 默认 `true` |
| `metadata` | `jsonb` | 扩展信息 |

如果不希望增加这张表，最低限度也要在 `subsystems` 中增加 `domain_code`、`domain_name` 两列，并保留 `source_domain_raw`。但从长期维护、重命名和分配筛选看，单独的域字典更稳妥。

### 4.3 “关联主功能”的处理：不要放进 `subsystems` 文本列

Excel 的 `关联主功能` 一格可以包含多行，例如 `M-113 中控锁`、`M-119 寻车`。这不是当前 `business_functions` 中的 AEB/LKA 业务功能；两者编码体系、职责和生命周期不同。

建议增加以下两个表，或在本轮先建 staging、后续确认命名后再正式化：

#### `system_main_functions`

| 字段 | 类型/约束 | 说明 |
|---|---|---|
| `id` | `uuid` PK | 稳定身份 |
| `project_id` | `uuid` FK | 当前按项目目录管理；如果确认全局共用，后续再拆全局目录 |
| `code` | `text` | 如 `M-101`；UQ(`project_id`,`code`) |
| `name` | `text` | 主功能名称 |
| `enabled` | `boolean` | 默认 `true` |
| `metadata` | `jsonb` | 扩展信息 |

#### `subsystem_main_function_links`

| 字段 | 类型/约束 | 说明 |
|---|---|---|
| `project_id` | `uuid` | 项目隔离键 |
| `subsystem_id` | `uuid` | FK `subsystems` |
| `main_function_id` | `uuid` | FK `system_main_functions` |
| `source_row` | `integer` | Excel 行号 |
| `source_text` | `text` | 原始关联行，保留审计和人工纠错依据 |
| `created_at` | `timestamptz` | 导入时间 |

主键建议为 `(`subsystem_id`, `main_function_id`)`。如果未来一个主功能可跨项目共享，再按真实业务确认后调整，不在本次导入中猜测。

`/` 的 4 条记录不产生主功能关系；它们应记录为“源表未提供关联”，不是空字符串主功能，也不是异常失败。

## 5. Excel 到数据库的映射

### 5.1 Staging 层

先建立一次性或可保留的 `stg_subsystems_excel`，不直接写正式目录。建议字段：

| staging 字段 | 来源 | 处理 |
|---|---|---|
| `batch_id` | 导入批次 | 每次导入唯一 |
| `source_file_name` | 文件名 | 记录来源 |
| `source_file_sha256` | 文件字节 | 防止同名文件被替换 |
| `source_sheet_name` | 工作表名 | `系统功能需求` |
| `source_row` | Excel 行号 | 3～45 |
| `source_domain_raw` | B 列合并值 | 展开后每行都有值 |
| `domain_code` | 解析结果 | 如 `BODY_1XX` |
| `domain_name` | 解析结果 | 如“车身” |
| `subsystem_code` | C 列 | 如 `SS101` |
| `subsystem_name` | D 列 | 原文清理首尾空白 |
| `description_raw` | E 列 | 保留换行 |
| `related_main_functions_raw` | F 列 | 保留原始多行内容；`/` 原样保留 |
| `parse_status` | 导入程序 | `ready` / `warning` / `rejected` |
| `parse_message` | 导入程序 | 重复、缺失、未知域等诊断 |

Staging 必须允许重复导入而不污染正式表；建议用 `batch_id + source_row` 做唯一定位，正式表使用业务唯一键。

### 5.2 正式表导入规则

1. 先导入/确认 `subsystem_domains`；域编码采用稳定内部编码，不直接以显示名称作为主键。
2. 以 `project_id + subsystem_code` 做幂等键；同一项目重复导入相同编号时不得无条件插入第二条。
3. 首次导入创建 `subsystems`，`enabled=true`、`catalog_version=1`、`source_kind=excel`。
4. `description` 按原文写入，保留换行；不因为描述里有“提供/控制”等句式而自动拆列。
5. 解析 `关联主功能`，仅对明确的 `M-数字/字母 + 名称` 创建 staging 关系；解析失败的行进入 warning，不丢原文。
6. `/` 作为 `no_related_main_function`，不创建关系记录；是否需要人工补充由导入报告决定。
7. 目标目录中已存在但源文件本批次没有的子系统，不自动删除或停用；必须生成差异报告，由管理员确认。
8. 已被 `allocation_targets` 引用的子系统只能 `enabled=false` 或归档，不能物理删除；名称变更保留同一 `id`。
9. 每次正式目录新增、停用、改名或描述变更都递增项目 `catalog_epoch`，并写入 `project_events`/审计记录。

## 6. 约束、索引与权限接口

### 6.1 必须有的数据库约束

- `subsystems.project_id` 不可为空；所有查询和写入必须带项目范围；
- UQ(`project_id`,`code`)；同项目不允许重复 SS 编号；
- `name`、`description`、`domain_id` 不允许为空；
- `catalog_version >= 1`；
- `enabled=false` 的目录项不得被新的已接受分配版本引用；历史版本仍可展示；
- 被 `allocation_targets` 引用的行禁止物理删除；
- `allocation_targets` 必须通过真实外键引用 `subsystems.id`，不能只保存 `subsystem_name`；
- 为 `project_id, enabled, code`、`project_id, domain_id, enabled`、`name`（项目内搜索）建立索引；
- 所有项目级关系必须用组合外键或服务端校验阻止跨项目引用。

### 6.2 权限能力点建议

V1.1 已有能力点模型，建议补充以下目录能力点，不把它们写成 `subsystems` 的列：

| 能力点 | 用途 |
|---|---|
| `subsystem.read` | 查看可用子系统目录和分配选择器 |
| `subsystem.manage` | 新增、修改、启停、归档子系统目录 |
| `subsystem.import` | 执行受控 Excel 导入/预览/提交 |
| `page.allocation.open` | 进入 FR 分配页面 |
| `allocation.read` | 查看分配对象及目标 |
| `allocation.update` | 修改分配目标 |
| `allocation.accept` | 接受分配版本 |

推荐的判断顺序：

1. 用户身份有效且属于项目；
2. 用户有项目/业务功能的进入权限；
3. 查看目录需要 `subsystem.read`；
4. 导入或维护目录需要 `subsystem.manage`/`subsystem.import`；
5. 修改 FR 的子系统目标还要有 `allocation.update`，不能因为有 `subsystem.manage` 就自动获得分配编辑权；
6. 后端/API 每次重新校验；前端只负责显示按钮、锁定态和提示。

## 7. 分阶段实施计划

### S0：确认目录语义与范围

- 确认这 43 条是否作为一个项目的正式初始子系统目录；
- 确认 Excel 中的 `M-xxx` 是否需要本期正式建模，还是只保留源文本；
- 确认 `domain` 是否允许项目后续新增/改名；
- 确认 `subsystems` 是项目级目录，当前 V1.1 默认如此；
- 确认 AEB/LKA 的 `business_functions` 与 M-xxx 主功能不直接关联。

### S1：生成导入预览，不写正式表

- 读取合并单元格并展开域；
- 生成 43 条子系统预览、8 个域、76 条主功能关联候选；
- 输出重复编号、缺失字段、未知域、无法解析的关联行报告；
- 人工核对 4 条 `/` 和多行主功能关系。

### S2：创建数据库对象

- 按迁移顺序创建 `subsystem_domains`（如采纳）、`subsystems`；
- 创建 staging 表或导入工具使用的临时 schema；
- 建立 FK、唯一约束、索引和禁止误删约束；
- 同期注册最小权限能力点，并把目录管理动作接入后端授权入口；
- 这一阶段不创建业务功能、PRD、UC、FR 数据。

### S3：事务导入初始目录

- 创建导入批次；
- 先写 staging，再通过校验的行写正式域/子系统；
- 写入 `source_kind=excel`、文件哈希、sheet 和行号；
- 若正式导入主功能关系，则在同一批次写 `system_main_functions` 和 link 表；
- 递增 `catalog_epoch`，记录项目事件和导入审计。

### S4：验收

- 数量：正式子系统 43 条、域 8 条、编号无重复；
- 关联：`/` 行不产生伪关系，主功能关系候选与源文本可追溯；
- 隔离：跨项目引用、跨项目更新、越权目录维护均失败；
- 分配：已停用子系统不能进入新的接受版本，历史分配仍可读取；
- 并发：目录变更递增 `catalog_epoch`，旧导入/分配任务按冲突规则处理；
- 备份：导入前有数据库备份或快照，失败可回滚整个导入批次。

## 9. 当前结论

可以进入下一步，但**还不应直接执行建表或导入 SQL**。权限架构已经在 V1.1 中设计完成，子系统表应按项目级目录实施，并由独立权限底座保护。推荐的第一批数据库对象是：

1. `subsystem_domains`；
2. `subsystems`；
3. 导入 staging；
4. 最小目录权限能力点及审计接入。

确认 SS-Q01、SS-Q02、SS-Q03、SS-Q06 后，再生成针对 PostgreSQL 18 的迁移 SQL、导入预览和逐条验收命令。当前没有执行任何服务器操作。
