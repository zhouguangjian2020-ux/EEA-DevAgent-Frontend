# 数据库设计精简审查与版本表必要性说明

> 审查日期：2026-09-20。  
> 依据：`数据库设计与实施方案_V1.1.md` + `项目级子系统划分与FR分配数据库设计_V1.2.md`。  
> 性质：**评审建议，等待确认；不替换现有设计基准，不是建表脚本。**  
> 本轮仅阅读本地设计、核对数据库机制并整理建议；未连接服务器、未执行 SQL、未修改业务代码。

## 1. 先给结论

**现有设计存在“部分机制为未来准备得过早”的问题，但“保留业务版本和来源关系”不是过度设计。**

前面的设计把基本业务、历史追溯、类型平台、审批、可靠事件投递等一并纳入目标范围，整体偏完整平台。对于当前准备逐步建库、先跑通 PRD → UC → FR → 分配的阶段，应该减轻实施负担，而不是一次落实全部机制。

建议采用以下取舍：

1. **保留内容快照、真实来源关系、项目隔离、后端权限、并发保护。** 这些直接支撑用户已经明确的业务。
2. **延期可重建的数据和高级能力。** 字段差异缓存、字段级影响证据、正式基线、复杂事件投递不必绑在首轮建库上。
3. **简化通用平台。** 固定类型的 metadata 可以由代码维护；固定目录未必需要可配置目录树；一项目唯一方案入口未必需要独立表。
4. **不要把版本保存等同于审批。** 有历史记录，不代表每一步都必须“接受／发布后才能继续”。这些流程门槛需要另外确认。
5. **不以表数量作为唯一指标。** 把全部内容、权限、关系塞进一个 JSON 表，表少了，但类型校验、查询和追溯不一定更简单。

当前目标表数为 **37 张一期表 + 5 张二期增强表 = 42 张**，不是已建表数量，也不是要求一次建完。后文列出 7 张延期或合并候选；若全部满足适用条件，一期目标可从 37 调整到 30 张。**30 不是“最少必须建 30 张”，也不是已经批准的新方案。**

## 2. 什么算本项目的必要复杂度

### 2.1 与明确需求直接对应，不能为了减表而丢失

| 业务要求 | 最小要保留的能力 |
|---|---|
| 多项目、项目间子系统划分不同 | 项目归属、同项目关联校验、项目自己的子系统身份 |
| 当前文档基准：项目下多个业务功能，每功能一个 PRD | 功能归属、PRD 唯一性，不混用 AEB/LKA 的对象 |
| PRD 是 Markdown 全文 | 保存全文；不强制拆成 PRD 章节业务表 |
| UC↔FR、FR分配↔子系统是多对多 | 真正的关联记录，而不是逗号拼接名称 |
| FR 与 FR 分配独立 | 独立分配身份和保存记录，修改分配不能覆盖 FR 正文 |
| 将来查修改影响 | 能还原旧内容、当时引用了哪个上游版本、当时选了什么子系统 |
| UC 浏览和编辑等权限分开 | 后端按动作与范围鉴权，不只是隐藏前端按钮 |
| metadata 告知类型及允许放置的内容 | 可读取的类型定义、后端校验；不强制要求全部定义都可在数据库里动态编辑 |
| AI 按“全部 UC／FR”分析，界面实时显示 | 保存任务输入集合、候选/正式边界、任务状态，以及刷新/重连后的状态回读 |

本审查沿用 V1.1 的功能归属口径，不重新改变 PRD 唯一性的范围。子系统“项目独立”已确认；单项目单正式方案、多级子系统、维护/发布流程仍是 V1.2 待确认事项。

### 2.2 不能作为删表理由的两个误判

- **“表里重复了 project_id，所以是冗余设计”**：关系中的 project_id、function_id、design_version_id 部分用于复合外键防串项目/串版本。应逐组检查约束用途，不能直接删掉这些字段。复合外键约束的是组合，而非每个 ID 单独存在。[PG-C]
- **“有了版本表就能自动知道哪些字段必须改”**：版本只说明历史内容和引用证据。哪些变化会造成工程语义影响，还需要规则、AI 或人工判断；不能把“依据过期”直接等同于“内容一定错误”。

## 3. 具体哪里偏重，以及怎么简化

### 3.1 七张可延期或合并的候选表

“延期”不是否定能力，而是先用更小方案实现明确需求；恢复触发条件列在最后一列。

| 优先级 / 原文位置 | 现有设计 | 审查结论与最小替代 | 代价与以后恢复条件 |
|---|---|---|---|
| 高；V1.1 §8.2 | `field_changes` 持久化每次字段 diff | **建议延期。** 先保留完整版本，用户比较时计算两版差异 | 少了预计算索引，批量查询差异可能更慢；出现高频历史分析/性能证据再建。它本来就被定义为可重建数据 |
| 高；V1.1 §6.2 | `artifact_type_versions` 在库中维护 schema、字段目录、UI schema 多套版本 | **建议先代码化。** 保留 `artifact_types`，类型定义和校验器随代码受控发布，内容版本保存 `schema_version` | 不能在管理界面动态发布类型定义。必须保留旧 schema/转换器，不能只删除 FK 而丢掉旧数据解释规则；用户确需运行时扩展类型时再建 |
| 中；V1.1 §6.8 | `workspace_views` 保存 renderer、布局、筛选及其版本 | **有条件延期。** 固定 UC/FR/分配全景从业务数据和默认配置派生 | 不保存服务端个人/共享布局、跨设备列设置。如这些已是一期明确需求，应保留；有全景页面不等于必有全景数据表 |
| 中；V1.1 §6.2 | `workspace_folders` 通用父子树 | **固定目录时可延期。** 由项目/功能/类型派生系统目录，继续返回目录 metadata | 暂不支持用户自建分组、重命名/移动目录和树结构持久化。若当前产品要自定义目录，不能删 |
| 中；V1.1 §6.2 | `folder_allowed_types` 多对多放置规则 | **与上一项一起处理，不能孤立删除。** 固定 UC 目录只能放 UC，由后端固定角色→类型映射验证；对象的归属和类型仍受数据库约束 | 不提供运行时自定义放置规则。必须同步调整 `artifacts.folder_id` 及相关组合 FK，不能留下半套目录模型 |
| 中；V1.2 §4.1 | `project_subsystem_designs` 一项目一行的方案入口 | **在“一项目只有一套方案”确认后可并入 `projects`。** 移入方案指针及独立的方案并发令牌 | 方案版本仍保留；不丢历史。一项目将来多车型/多并行方案时，才需要真实的方案身份实体。也可因模块隔离保留此表，不是严重错误 |
| 中；V1.1 §7.1–7.2 | `project_events` 事务 outbox、项目严格事件序号、断线重放 | **若一期无可靠事件回放/跨服务通知要求，可延期。** 任务和候选仍落库，前端轮询或 SSE 通知后重新查询；断线后重新拉状态 | 不保证每条事件可靠投递、按历史逐条重放；只保证能读到持久化的最终/候选状态。若这些保证是交付要求，应保留 |

**计数核对：** 37 − `field_changes` − `artifact_type_versions` − `workspace_views` − `workspace_folders` − `folder_allowed_types` − `project_subsystem_designs` − `project_events` = **30**。这是上述条件全部成立后的目标，不包含后文其他可选精简，也不包含二期五表。

不建议为了凑到 30 张，把已明确的自定义目录、持久化布局或可靠通知需求一起删掉。

### 3.2 不一定减少表数，但最值得降低的复杂度

#### A. “所有上游必须接受、无任何旧来源，才能生成下一阶段”过早变成硬门槛

位置：V1.1 §7.1–7.3、§8.1；V1.2 §6。

保留历史版本、生成输入快照是必要的；但以下是不同的产品决策：

- 必须每条 UC 人工接受后才能生成 FR；
- 任意 UC 有新草稿就阻断整个功能；
- 所有 FR 分配必须等待独立方案发布人；
- 一个小修改使整批下游必须重新生成。

**建议**：保留“保存”和“接受”的能力（如界面确实需要），但先不要把所有接受动作做成跨阶段强制闸门。下一阶段可以固定使用经过用户选择/确认的保存版本，明确标识未审阅和来源变化，不允许静默混用。是否允许这么做，由用户确认，不能本轮自行更改既有流程。

`head_revision_id` 与 `accepted_revision_id` 只有在“编辑版和确认版可同时存在”时才需要同时存在；如果没有这个业务区别，一个 current 指针就够。不能仅因为数据库能做审批，就要求用户多点几次按钮。

子系统也同理：可以“保存即生效并留版本”，也可以“草稿→发布”。**不同项目划分不同，不自动推出必须采用双阶段发布。**

#### B. 角色定义的不可变版本和批量绑定迁移，初期偏重

位置：V1.1 §13.5.3。

`access_roles` 本身值得保留，`role_permissions`、`access_bindings` 也有实际业务价值；偏重的是初期只有预置角色，却要求每次调整生成新角色版本、迁移授权绑定。

**简化方向**：预置角色定义随代码/迁移受控管理，不开放通用角色编辑器。若允许原地调整角色能力，必须明确影响所有绑定者，并有变更预览、审计、权限缓存失效及发布时重新鉴权；绝不能把“取消角色版本”解释成“角色可以随便改”。若业务需要各项目继续使用不同旧角色策略，就保留版本化角色。

#### C. AI 多 worker 租约、接管与恢复机制可延后

位置：V1.1 `ai_runs.lease_owner/lease_expires_at/attempt_no`。

第一阶段只有单实例执行器时，可先明确服务重启后旧任务被标记中断/失败，由用户重试。暂不承诺自动恢复模型流、跨 worker 无缝接管。

**不能省**：幂等请求、持久化状态、旧任务不得覆盖新编辑、完成提交时再次鉴权、完整产物原子落库。即使暂不自动接管，也要防止过期执行者继续提交。

#### D. 目录快照与失效信号有重复维护风险

位置：V1.1 §7.1；V1.2 §6.3。

- `ai_runs.subsystem_design_version_id` 已固定不可变方案，可以从版本条目重建子系统目录。**一般不再存一份完整 `catalog_snapshot` JSON。** 若确实需要精确保留“发给模型的裁剪/排序/转换后输入包”，应记录真实输入包及转换规则版本，而不是又复制一份未经转换的目录。
- `allocation_targets.subsystem_name_snapshot` 已在 V1.2 标为可省略，继续省略，历史名称从固定版本条目读。
- 在只能发布新版本、不能把正式指针来回切换的前提下，AI 结果提交时比较所选方案 ID 和当前有效方案 ID，通常已能判断方案是否变化；`catalog_epoch` 不一定还要作为另一套强制冲突信号。若保留它做缓存失效，写清用途。
- `input_set_hash` 与功能 `data_epoch` 不应是两套语义不清的“版本系统”：一者代表确切输入集合，一者是粗粒度失效序号。可先保留一种可靠的集合变化检查方法，但**必须发现新增/归档 UC，不是只比较已引用 UC 的内容**。
- 项目/功能全局 epoch 很保守：无关 FR 的保存可能让 UC 生成冲突。这是简单保守策略的代价，不是业务必然要求；不要为修复它立即扩展成很多复杂计数器，先明确读集合、写目标及验收案例。

#### E. 不要因为三个页面就建三套子系统内容

“子系统列表”“子系统具体划分”“FR子系统分配”是三个操作入口，不是三份独立子系统字典。V1.2 用稳定身份、方案快照和独立分配来区分职责，方向正确。

若只是为了让各项目灯系统名字不同，`subsystems(project_id, ...)` 已能隔离。**方案版本另外解决的是：同一项目后来改名、拆分或合并时，旧分配还能准确回看。** 在用户还要未来追溯的前提下，我建议保留这项历史能力，但不强制复杂审批流程。

### 3.3 已经放在二期的五张表：不算误放一期，但不要提前实施

- `trace_field_links`：字段级来源证据。
- `impact_analyses`、`impact_items`：影响检查任务与逐项处理。
- `baselines`、`baseline_items`：跨对象冻结的正式交付集合。

它们有真实用途，但**不是“有追溯”就必须马上具备的全部能力**。先实现版本级来源查询、内容对比和候选影响提示，再看是否需要工作流化管理和正式基线。

## 4. 什么不建议为了减表而删除

### 4.1 `artifact_revisions` 与 `*_versions` 不是两份正文

可以把它理解成“一份文件的公共封面 + 对应类型的正文”：

```text
artifact_revisions：UC-001 的第 3 版，谁在何时保存、从哪版改来、AI任务是什么
                │ 同一个 revision_id，1:1
uc_versions：   这一版的名称、描述、参与者、前后置条件等
                └─ uc_scenario_items：这一版的分支与异常内容
```

前者不保存第二份 UC 正文；两者组成**同一个业务版本**，不是分别升级的两个版本。

这套垂直拆分的收益是：权限、任务输入、历史入口和来源指针可以引用统一的对象/版本 ID；代价是 JOIN、写事务和“必须有正确类型子表”的完整性校验。

也存在另一条有效路线：不用公共版本头，四类版本表各自保存作者、版本号、时间等。但必须成套重做任务输入、公共审阅、版本引用和类型安全约束。**不是删一张 `artifact_revisions` 就完成简化。** 在保留现有统一对象体系的方案中，建议继续用版本头。

### 4.2 身份表不等于内容历史表

| 表 | 为什么存在 | 是否能简化 |
|---|---|---|
| `artifacts` | 四类对象统一且稳定的 ID，保存当前/接受指针，作为对象权限和标签定位入口 | 当前公共架构下保留 |
| `prds` | 表达一个功能的 PRD 身份与唯一性 | 可整体改成 artifacts 的类型唯一约束，但会连带调整 UC 来源和类型 FK；本轮不建议单删 |
| `use_cases` | UC 的稳定身份和所属 PRD，不因正文改动而换对象 | 保留 |
| `functional_requirements` | FR 类型身份，给分配等提供受类型约束的引用目标 | 它目前是薄表，可在未来整体类型模型重构时合并；不是首要优化点 |
| `fr_allocations` | 独立分配对象，把“这个 FR 的分配”与 FR 正文分开 | 保留，符合用户明确要求 |
| `subsystems` | 子系统稳定身份；改名不改 ID，真正拆并可以形成新身份 | 保留；不能只用名称关联 |
| `project_subsystem_designs` | 工作版/正式版指针及方案编辑锁的容器，不是历史正文 | 一项目唯一方案时可并入 projects，见 §3.1 |

减掉薄身份表可能节约一次 JOIN，却增加多态 FK 和类型一致性约束。应在迁移草案中一起评估，不因为“字段少”就直接判成过度设计。

### 4.3 关系版本化并非把同一条关系无意义地复制

`FR-001 r1 → UC-001 r2` 与 `FR-001 r2 → UC-001 r3` 是两条不同历史事实。只保存当前一条关系，会让旧 FR 看起来也基于新 UC，这会破坏追溯。

同理，改了分配目标后，应保存新分配版本的新目标集合，不覆盖旧版本的 `allocation_targets`。

## 5. 先分清“版本”的不同意思

| 名称 | 它回答什么 | 不是用来回答什么 |
|---|---|---|
| 对象 ID | 这是哪条 UC/FR？ | 正文当时是什么？ |
| 内容版本 | 这条对象第几次保存，保存了什么？ | 当前谁有权看？ |
| 来源版本关系 | 这版 FR 依据的是哪几版 UC？ | 字段变更是否一定造成工程影响？ |
| 类型结构版本 | 这份旧数据按哪套字段/校验规则理解？ | 某条 UC 的业务内容第几版？ |
| 子系统方案版本 | 当时整个项目怎样划分、每项叫什么/负责什么？ | 所有项目共享同一套名单？ |
| 权限角色版本 | 当时这套角色包含哪些能力？ | 当时业务正文是什么？ |
| 项目基线 | 某次交付冻结了哪些对象版本组合？ | 各对象各自的全部修改历史？ |
| 并发令牌/epoch | 我读取后是否有人修改、缓存是否失效？ | 历史正文如何还原？ |

**把一行的 `version` 从 1 改成 2，同时覆盖正文，并没有保存第 1 版。** 历史需要持久保留旧内容或有可靠的重建链；本设计建议完整业务快照，不做必须逐个重放的差量链。

数据库内部 MVCC 也不等于产品历史版本：PostgreSQL 会回收更新/删除产生的旧行空间，不能拿它代替可长期查询的 UC/FR 历史。[PG-V]

## 6. 逐张解释：直接保存版本内容或定义的表

### 6.1 一期建议保留的七张内容版本表

| 表 | 保存什么；示例 | 删除且不做替代，会失去什么 | 建议 |
|---|---|---|---|
| `artifact_revisions` | 公共版本头：对象、r序号、作者/时间、前版、AI来源、schema标识；如 UC-001 r3 | 统一版本引用、公共历史入口和版本创建证据；可改其他架构，但不能直接删 | **当前架构保留**，不是第二份正文 |
| `prd_versions` | 一版完整 Markdown；如 PRD r1 的全文 | PRD 修改后，不能还原 UC 当时依据的需求说明 | **保留**；PRD 仍是一段 Markdown，不拆业务字段 |
| `uc_versions` | 一版 UC 字段及所依据的 PRD 版本 | UC 改动前后的内容、生成 FR 时的真实 UC依据 | **保留** |
| `fr_versions` | 一版 FR 描述；来源集合另见 `fr_uc_sources` | FR 变更前的要求、分配当时使用的 FR 正文 | **保留** |
| `allocation_versions` | 一版分配决定：FR版本、子系统方案版本、备注；目标另见 `allocation_targets` | 谁把哪版 FR 分给当时哪套划分，旧分配会被新选择覆盖 | **保留**，符合 FR 与分配分开管理的需求 |
| `subsystem_design_versions` | 一套项目划分的版本头，实际完整内容由同版条目构成 | 不能准确重建“当时采用的整套划分”及方案换版顺序 | **为历史追溯建议保留**；是否草稿/发布双阶段另外确认 |
| `subsystem_version_items` | 某方案版的完整子系统清单及每项当时的名称、职责、分组、可分配性 | 改名/拆并后，旧分配会错误显示新职责或找不到原目标 | **保留**；它不维护另一套独立版本序号，而是方案版本的正文集合 |

这里的“七张”只数上表，不把身份表、关联表或 schema 表算进去。FR/分配的“完整快照”包括其关联记录，不只是正文那一行。

### 6.2 `artifact_type_versions`：结构版本，不是业务内容版本

例如 UC schema v1 固定 4 个分支，未来 v2 改为可变数量。即使同一条 UC 内容已经到 r20，它仍可能符合 schema v1；两个编号不能互相替代。

- **保留结构版本信息的必要性**：旧数据需要按旧规则解释，不能因新增必填字段就突然全部不合法。
- **独立建这张表的必要性**：当前四类对象字段由代码和前端固定控制，没有用户动态配置类型的明确需求，数据库表本身不是现在必须的。
- **建议替代**：在内容版本保留 `schema_version`；按 `(type_code, schema_version)` 保存受控的代码定义，metadata API 仍返回字段目录、类型、允许项。服务端拒绝未知版本，并保留旧定义/兼容读取路径。
- **影响范围**：替换 `artifact_revisions.type_version_id` FK；二期 `trace_field_links` 的字段校验改为同样的定义查询；更新导入、API校验与旧版读取测试。不能只删一张表，其他契约不动。

## 7. 逐张解释：看起来不像版本表，但属于版本链的表

### 7.1 内容子项与真实来源关系

| 表 | 与版本的关系 | 必要性/建议 |
|---|---|---|
| `uc_scenario_items` | 分支、异常挂到指定 UC版本；item_id 跨版定位同一项，内容随父版保存 | **内容必须保留**；单独成表不是唯一办法。若改 JSONB 数组也必须保留固定字段键/稳定项ID和验证能力；现有结构清楚，本轮保留，不建立场景项独立审批/独立版本流程 |
| `fr_uc_sources` | 某一 FR版本实际依据哪些 UC版本，多对多 | **必要**。不能替换为任务输入全集，也不能只留当前 UC ID |
| `allocation_targets` | 某一分配版本选择哪些方案条目，多对多 | **必要**。不因只比 FR 多了子系统名称就合并回 FR；design_version_id 用于同版目标约束，不是重复正文 |

### 7.2 AI 任务与输入输出

| 表 | 它回答的问题 | 必要性/建议 |
|---|---|---|
| `ai_runs` | 谁发起哪次生成，模型/参数/模板是什么，成功/失败/冲突如何？ | **保留简化版**。它不是内容历史替代品；先不实现多 worker 自动恢复 |
| `ai_run_inputs` | 这次任务到底读了哪些对象的哪些版本？ | **建议保留**。用户要求“所有 UC/FR”参与分析；某 UC没有成为任何 FR 的实际来源，也可能参与了这次推理，不能从 `fr_uc_sources` 完整反推 |
| `ai_run_outputs` | 批量任务各产物的稳定键、候选/正式/拒绝状态、冲突基版是什么？ | **在实时批量候选预览下建议保留**。仅查 artifact_revisions.ai_run_id 能查出处，但不能取代独立候选状态和幂等 output_key。若只支持任务结束后一次性落正式结果，可以另行简化，不能既删候选模型又承诺实时逐条恢复 |

`ai_run_inputs` 保存完整输入集合；`fr_uc_sources` 保存逐条 FR 的实际依据子集；`ai_run_outputs` 保存生成过程的产物登记。三者不是一回事。

保留模型配置和输入版本有利于解释来源，但不保证重新调用 AI 一定逐字复现同样输出。

### 7.3 审阅、差异和二期影响分析

| 表 | 它回答的问题 | 必要性/建议 |
|---|---|---|
| `review_events` | 谁接受/拒绝/撤回了哪一个版本？ | **有接受流程就保留**；不保存第二份正文。若只要求保存生效、不区分审阅，表和 accepted指针可一起延期，不能单独删事件但继续宣称有完整审批历史 |
| `field_changes` | r2 与 r3 哪些字段不同？ | **现在可延期**，从快照按需比较；不是保存历史的前提 |
| `trace_field_links` | UC某版某字段到 FR某版某字段有什么支持证据？ | **二期**。需要可审核证据时再建；版本级来源先满足基本追溯 |
| `impact_analyses` | 某次影响检查基于哪两版差异、何时检查、是否完成？ | **二期**。将“一次查询”升级为可管理任务时才需要 |
| `impact_items` | 每个潜在受影响项的判断和处理结果是什么？ | **二期**。需要指派、复核、关闭和处理留痕时才需要；无影响结论只对分析版本有效 |

### 7.4 基线

| 表 | 它回答的问题 | 必要性/建议 |
|---|---|---|
| `baselines` | “第一轮评审版／交付版”这个集合叫什么，谁何时冻结？ | **二期**；只有正式冻结/交付的明确需求时纳入 |
| `baseline_items` | 该集合选择 PRD r2、UC-A r3、UC-B r1、FR-A r4 等哪些固定版本？ | 与 baselines 配套；不复制正文。只有各对象历史并不能自动给出某次经过确认的组合 |

现设计的 `baseline_items` 只引用 artifact版本。V1.2 子系统方案不在 artifact体系里：通过分配可以找出被引用的旧方案，但**不能据此完整表达一个项目基线选定的方案（尤其尚无分配时）**。若将来实施基线，应明确增加本项目所选方案版本及依赖闭包规则；本轮不为二期提前增加表。

### 7.5 权限政策版本、审计、事件和视图

| 表 | 与“版本”的关系 | 必要性/建议 |
|---|---|---|
| `access_roles` | 当前以 `(code, version)` 保存角色定义版本 | **角色需要，不可变角色版本不一定现在需要**。见 §3.2B |
| `role_permissions` | 某一角色定义/版本的能力集合 | **保留能力关联**。不等于业务内容版本 |
| `access_bindings` | 某用户在项目/功能/对象范围绑定哪个角色版本 | **保留范围授权**。是否绑定不可变版本取决于角色策略，不是正文历史机制 |
| `security_audit_events` | 授权修改前后状态、操作者和敏感操作证据 | **保留权限变更审计**。取消角色版本不等于取消审计；它也不能代替 UC/FR 内容快照 |
| `project_events` | sequence 用于通知顺序/续传，payload可携带 revision引用 | **可条件延期**。事件流不是完整正文历史，不应依赖重放它来还原所有业务内容 |
| `workspace_views` | renderer_version 是展示配置格式，lock_version 是编辑冲突令牌 | **视图配置有需求才存**。二者都不是 UC/FR 内容版本 |

### 7.6 边界核对：没有遗漏其他隐藏的内容版本表

- `projects`、`business_functions`：承载当前归属、epoch；若合并方案入口则也承载方案指针，不保存正文历史。
- `app_users`、`project_members`：身份/成员资格，不是内容版本表。
- `permission_definitions`：能力目录，不是对象内容版本；变更仍需受控。
- `artifact_types`：类型注册身份，不是内容版本。
- `workspace_folders`、`folder_allowed_types`：目录与放置规则，当前未设计成独立历史版本。固定目录方案可按 §3.1 简化。
- `artifacts`、`prds`、`use_cases`、`functional_requirements`、`fr_allocations`、`subsystems`、`project_subsystem_designs`：身份/指针表，已在 §4.2 逐张说明。

至此覆盖 V1.1 + V1.2 的全部 42 张目标表。`v_*` 查询/SQL VIEW、可选域字典、模板及拆并映射不属于这 42 张，不能误加进已批准建表清单。

## 8. 这些“版本字段”是不是也必须保留

| 字段/概念 | 实际用途 | 精简原则 |
|---|---|---|
| `revision_no` / `version_no` | 给人看的每对象/方案递增版本序号 | 保留；不同对象编号相同不意味着同一批次 |
| `head_revision_id` | 当前工作版本定位 | 保留 current/head之一；不会因字段叫 head 就自动具备分支合并能力 |
| `accepted_revision_id` | 最近被确认、可与工作版不同的版本 | 有确认流程才需要 |
| `base_revision_id` / `parent_version_id` | 本次修改从哪一版开始；记录来源和冲突基准 | 建议保留，不表示必须开发 Git式分支、合并算法 |
| `working_version_id` / `published_version_id` | 子系统工作方案与正式方案双头 | 双阶段流程确认后保留；否则可用一个有效版本指针 |
| `base_published_version_id` | 编辑期间正式方案是否已经变化 | 仅在存在独立工作/正式版生命周期时保留 |
| `lock_version` | 防止编辑者基于旧状态覆盖别人提交 | 保留一种可靠 CAS机制；如果现有 revision指针比较已覆盖所有可修改状态，可评估去重。只有正文指针变化检测不能自动覆盖审阅/归档变化 |
| `data_epoch` | 功能输入集合/缓存的粗粒度失效 | 可简化范围，但不能漏掉新增/归档对象；不保存内容 |
| `catalog_epoch` | 子系统正式方案变化计数 | 已有不可变方案ID比较时评估去重；有缓存/事件用途则独立说明 |
| `authz_epoch` | 授权缓存失效 | 有授权缓存时很有用；无缓存可实时查权。最终写入始终重新鉴权，不靠旧epoch授予权限 |
| `event_sequence` | 事件续传游标 | 随持久事件重放能力延期/保留；不当作对象版本 |
| `content_hash` / `input_set_hash` | 内容去重/集合一致性摘要 | 不是完整历史、不是授权。规范化算法要固定；没有消费方的摘要字段可以暂不建 |
| `prompt_template_version` / `model_id` | 解释生成配置 | 作为任务元数据保留，无需因此另建一套通用模板版本平台 |
| `renderer_version` / `schema_version` | 配置或数据格式如何解析 | 保留真正需要的兼容标识；不与业务 revision混为一谈 |

## 9. 用你的灯系统例子串起来

### 9.1 跨项目差异

```text
复杂项目 A：方案 A-v1
  A-S01 内灯控制系统
  A-S02 外灯控制系统

简单项目 B：方案 B-v1
  B-S01 内外灯控制系统
```

A 和 B 的子系统 ID、归属和方案都独立。同名/同编号不代表同一条记录。这个需求首先由项目级归属解决，不是靠全局字典里增加一个“版本号”解决。

### 9.2 同项目后来变化

假设简单项目 B 的 FR-010 r1 被分配给 B-S01：

```text
UC-001 r2 ──实际来源──> FR-010 r1
                              │
                              ▼
                       分配-010 r1
                         FR依据：FR-010 r1
                         方案依据：B-v1
                         目标：B-S01（当时叫“内外灯控制系统”）
```

项目 B 升级后，新方案 B-v2 拆成 B-S02 内灯、B-S03 外灯：

1. 新方案保存新条目，不覆盖 B-v1。
2. 旧分配 r1 仍指向 B-v1/B-S01，回看时还能显示当时的名称和职责。
3. 根据旧方案形成的分配进入候选复核清单；**不是一律宣布需求错误**。
4. 确认 FR-010 只由外灯负责后，建立分配 r2，固定 B-v2/B-S03。
5. 如果 FR 正文没有改变，不为了方案换版而伪造一个 FR正文版本；分配可以独立升级。

再假设 UC-001 从 r2 修改为 r3：可以查出 FR-010 仍引用 UC r2，提示来源变化；如果分析确认 FR正文要改，则建立 FR r2，再检查引用旧 FR 的分配。仅发现版本不同，不能自动决定正文怎样改。

这几步需要正文版本、来源关系、方案版本和分配版本；**不要求先有字段差异表、基线、类型管理后台或复杂审批引擎。**

## 10. 保存策略：不要把版本做成“每个字一版”

建议默认如下，具体频率和保留期限另定：

- 输入中/AI逐token：不写业务版本；需要自动保存时使用草稿机制，不把每次敲字都纳入正式历史。
- 用户显式保存有效修改：建立新内容快照；无内容/关系变化时可作为无变化保存，不强制造一版。
- AI完整产物：先保存可恢复候选；采纳/发布时更新当前指针，同一份候选不因为点击“采纳”再复制一次正文。
- 只做接受/拒绝决定：保存审阅事件，不为完全相同正文再建一个内容版本。
- 改来源集合或分配目标，即使正文文本没变：属于业务快照变化，应生成相应新版本。
- 恢复旧内容成为新的正式工作结果：以旧快照创建新版，保留“恢复自哪版”。与“取消尚未接受的草稿，重新显示原已接受版”区分；后者是可审计的指针/审阅操作，不是抹掉已生效历史。
- 已被来源、分配、任务、审阅或基线引用的历史不得随意清理。草稿/失败候选的保留策略单独制定，不把所有类别统一永久保留，也不盲删旧版本。

完整快照会增加空间，但当前还没有对象数量、保存频率、正文大小和保留期限数据，不能编造“占用很小”或“必须立即差量压缩”的结论。先记录增长并做容量测试，再确定归档/压缩方案。

## 11. 建库前必须同步修正的设计问题

这些不全是过度设计，也包括 V1.2 并入之后的契约一致性问题。

1. **旧图不再完整。** V1.1 原图尚未覆盖三张新增方案表；README已提示。实际迁移应先整理最终确认版全图，不能照旧图独立建表。
2. **约束清单摘要仍有旧子系统字典口径。** V1.1 §10.1 第7项只写到 `allocation_targets` 引用共享子系统；V1.2/§6.7 已要求同时约束方案版本及版本条目。迁移清单要合并，不能只约束 subsystem_id存在就当完成。
3. **基线尚未覆盖项目方案的显式选择。** 见 §7.4，二期实施前补齐，不现在扩表。
4. **子系统方案不在四类 artifact里。** 所以不能把方案UUID写入只接受 artifact的 AI输入或对象授权字段。当前分配任务的显式方案FK可以继续用；项目级“AI生成架构方案”若未来开发，要先明确任务scope，不能挂到假AEB功能下。
5. **审阅/发布/候选术语偏多。** 必须统一“保存工作版”“接受内容”“生效方案”“AI候选正式落库”的区别，不要让一个 publish同时代表几件事。
6. **每个冗余索引和计数器都应有消费者。** 复合FK需要的唯一键不能随便删，但等价/前缀重复索引应在迁移时核对；当前没有测量数据，不宣称一定出现性能瓶颈。
7. **不可变不能只写在注释里。** 需要受控写入路径、权限边界、完整事务和测试；类型版本头与子表“不能缺正文”等跨表规则不能靠普通行级CHECK假装完成。[PG-C]

## 12. 推荐的实施取舍

### 第一层：先锁定不变的业务骨架

- 项目/业务功能/用户与成员、最低可用权限。
- PRD、UC、FR、独立分配的身份与内容版本。
- UC场景、UC→FR真实来源、FR版本→分配、分配→本项目方案条目。
- 每项目独立子系统身份及方案历史，避免后续改名/拆并破坏旧分配。
- 必要事务、归属校验、幂等和防覆盖，不实现自动跨版本合并。

### 第二层：接 AI 与界面实际需要的生命周期

- 持久化 AI任务、完整输入集合、候选输出。
- 若界面有接受动作，保留审阅事件；是否阻断下游另外确认。
- 实时画图/表通过正式状态与候选状态查询产生，不复制全景正文。
- 先选清楚状态回读还是可靠事件重放，不默认两套全做。

### 第三层：需求出现再加的增强

- 可配置类型平台、任意文件夹、跨设备共享布局。
- 多执行器自动接管、事务outbox和事件回放。
- 字段diff索引、字段证据、影响处理闭环、正式项目基线。

这里的实施顺序不是要求首轮手动把全部30/37张都建好。每一步都先给迁移方案、回滚/验收办法，再由用户手动执行；助手不连接服务器。

## 13. 需要确认的少量产品问题

本轮可先接受审查结论，不要求现在一次回答所有细节。后续精简成新基准前优先确认：

1. PRD/UC/FR是否必须逐条接受后才能给下一阶段使用，还是保存后可明确选择版本继续生成？
2. 子系统修改是“保存即生效”，还是必须另设草稿和发布？单项目是否始终一套当前有效划分？
3. 一期文件夹是否固定，是否需要用户自己建目录/分组以及跨设备保存全景布局？
4. 断线后重新读取任务/结果是否足够，还是必须完整回放每条变更通知？

不重复询问已经明确的“每项目独立划分”“FR与分配分开”“UC↔FR多对多”。
